# phase-03-service-and-ui — risks

> **Authority.** This register owns the phase-level risks. A module's own risks
> live in its directory; each entry here names a trigger, an impact, a
> mitigation and the version that owns it.

| Id | Risk | Trigger | Impact | Mitigation | Owning version |
|---|---|---|---|---|---|
| R20 | A message catalogue drifts from the markup: a string is added to the markup directly and never reaches the catalogue, so the page ends up half translated and nobody notices until a user does. | A new control is added by editing the markup. | The interface is Chinese everywhere except one label, which reads as carelessness rather than as a bug. | The markup carries structure only and every visible string is filled from the catalogue; a test compares the two languages' key sets, and the DOM contract test rejects a visible literal in the markup. | see [../VERSIONS.md](../VERSIONS.md) |
| R21 | A shared value is copied "just this once" because the two sides cannot import each other. | A browser-side module needs a number the service also uses. | Two copies of a limit, and the one that drifts is always the one the user sees. | The shared module lives where both sides can import it — the page's own directory, which the service also reads — and a test asserts the two callers agree at a boundary. Where a copy is genuinely forced, the reason and a test are recorded instead. | the version naming M00 |
| R22 | The interface offers a rate or a size the core refuses, because the page was written before the limit moved. | The core's bounds change, or a new control hard-codes one. | A control that produces an error instead of an action. | The core advertises its limits in the handshake and the interface applies them, asserted against a stub handshake carrying non-default values. | the version naming M00 |
| R23 | Recording every generation costs more than the run it records, so a session is slow because it is being remembered. | A long run at a high tick rate with a history enabled. | The feature that makes a run reproducible makes it unusable. | Deltas rather than snapshots, a keyframe interval that bounds the replay walk, and a measurement of the recorded path against the unrecorded one recorded in the store's `performance.md`. | the version naming M00 |
| R24 | The history database grows without bound. | A long-running session, or many sessions in one store. | A file that outgrows the repository it is confined to. | The store records a measurement of bytes per generation, and retention is a decision this phase has not made: it is listed as an open question until it is. | the version naming M01 |
| R25 | Rollback after an edit produces a chain that cannot be replayed, because an edit is not a step. | A cell is toggled between two recorded generations. | A rollback that refuses, or worse, silently restores the wrong state. | A mutation re-keyframes its own generation, and the store's replay validates every delta, so an unreplayable chain is refused rather than applied. | the version naming M00 |
| R26 | The interface is translated but the domain language is not: a term is translated word by word and stops meaning the same thing. | A term is translated without deciding what it means in Chinese. | A user who reads Chinese cannot tell "generation" from "step". | Terms are decided once in the catalogue with a comment, and the same term is used for the same concept everywhere, including the readouts. | the version naming M00 |
| R27 | **Reproduced in the wild.** A viewer's core outlives the service that started it: after an end-to-end run, one `node` and two `python` processes were still alive about fifteen minutes later, holding `data/history.db` and its `-wal` and `-shm` sidecars. A forced kill from the agent's own shell reported success and did not take effect; the processes exited on their own later, releasing the files. | A service is stopped in a way its teardown does not observe — killed, crashed, or a test that removes its store before the core has let go. | Two cores can write one history database. The visible symptom is an `EBUSY` on a file nobody is deliberately using; the invisible one is a second writer, which the store does not detect. This is the same defect the version naming phase 02 milestone 02 fixed *inside* a test teardown, and the fix did not generalise to an operator killing the service. | Recorded in the viewer's own register as VWR-17. The fix that version applied — stop the core explicitly before removing its store — is necessary and not sufficient: what is missing is a core that gives up the store when its parent disappears, or a store that detects a second writer. | the version naming phase 03 milestone 02, whose subject is more than one session per service, because two sessions is exactly where two writers stop being hypothetical |
| R28 | A page grew into three concerns. The world, the history and the archives shared one document, so a change to any of them risked the other two, and a reader had to hold all three in mind. | A fourth concern arrives. | The page becomes the thing that is hard to change, which is the cost this project's documentation rules exist to avoid, applied to code instead of prose. | Split into routed tabs with the layout and the shared modules in one place and one module per tab. A first attempt was made, reached a green test suite, and was then reverted uncommitted when a user reported the pages blank — so the work has to be redone, and what the attempt learned is recorded in `docs/model/viewer/implementation.md` rather than lost with it. The lesson that outlives the attempt: the two defects a *person* saw were invisible to the tests, because a synthetic document conjures an element on first lookup and a stylesheet is not evaluated at all. | the version naming phase 03 milestone 01, which attempted the split |
| R29 | **A synthetic document cannot see a missing element.** The stub used by the browser tests creates an element the first time a script looks one up, so a page whose markup omits a container the script expects still passes every test — and the script then returns early in the real browser and draws nothing. | A page's markup and its script disagree about an id. | A blank region that no test fails on, found by a person instead. | The stub's lookup must return null for an id the markup does not declare, and a contract test must assert that every id a page's script reads is declared by that page's markup. The first attempt at routed tabs failed exactly this way: the history page lost its `#timeline` and drew no tree. | the version naming phase 03 milestone 01 |
| R30 | **A stylesheet is never evaluated**, only read. The audit checks that a class the stylesheet names appears somewhere; it cannot check that a selector matches an element at runtime. A renamed class therefore leaves rules that apply to nothing, and a person sees an unstyled control while every test passes. | A selector's subject is renamed in markup. | The three panel states were completely unstyled in the browser while their logic was covered by tests. | The audit requires a class to appear where a class is *borne* (`class=`, `className=`, `classList.add`) rather than anywhere in the file, which found two groups of rules that applied to nothing. Closing the gap fully needs a browser or a CSS engine and is not claimed. | the version naming phase 03 milestone 01 |

## Open questions

| Question | State |
|---|---|
| Does a representation switch continue the same recorded session or start a new one? | Answered: it continues. The replacement core adopts the session the previous core was recording (`--continue-session`), so the node count is unchanged by the switch and the next step appends to the same session. The case is part of the version in progress (`v0.3.7`). |
| How long should a history be kept, and what evicts it? | Open. Nothing evicts today; the file grows. A retention rule needs a measurement of bytes per generation first. |
| Should the core's diagnostic messages be translated? | Answered: no. They are read by whoever is diagnosing a fault, they name the code that raised them, and translating them would make a report harder to search for. The interface's own labels are translated. |
| Do the phase's task and acceptance tables cover every delivery in this phase? | Open, and owned by the version naming phase 03 milestone 06 in [../VERSIONS.md](../VERSIONS.md). Two deliveries have no task in [tasks.md](tasks.md) and no criterion in [acceptance.md](acceptance.md): the preview default and the browser probe tool, and the rule editor. Their acceptance is in their own `dev-log` entries and the version table names them, but the phase core does not. Reconciling means either adding the missing entries with the evidence those entries hold, or declaring the `dev-log` the acceptance record for deliveries after M02. |
