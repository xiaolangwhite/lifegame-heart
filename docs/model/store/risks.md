# store — risks

> This file owns the risks that are still open and the questions that are still
> unanswered. Every entry carries a trigger, an impact, a mitigation and the
> **version that owns it**; an unresolved item without an owning version is a
> defect, and the ones in that state are reported in §3 rather than left implicit.
> What the module promises is owned by [interfaces.md](interfaces.md); what was
> measured is owned by [performance.md](performance.md).

## 1. Open risks

| Id | Risk | Trigger | Impact | Mitigation | Owning version |
|---|---|---|---|---|---|
| STO-01 | The MySQL round trip has never been executed. The SQL is verified; no generation has been written to or read from a MySQL server by this project | A user points the store at a server | The feature is claimed for a backend whose end-to-end path is untested. A dialect difference that only appears at run time — a length limit, a transaction semantic, a type coercion on `LONGBLOB` — would be found by that user | The schema, the DDL and the parameter translation are executed by tests that need no server ([testing.md](testing.md) §1); the scope statement and the three commands that would close the gap are in [testing.md](testing.md) §8; the decision is [ADR 0011](../../adr/data-and-formats/0011-sqlite-default-mysql-supported.md) | the version naming phase 02 milestone 02 in [VERSIONS.md](../../plan/VERSIONS.md). The item cannot be closed by that version on this machine, which has no server; it closes on the first machine that has one |
| STO-04 | Nothing compares the world handed to `record` or `rollback` with the size the session declares | A caller opens a world of a different size than the session recorded | A rollback into a larger world is silent and succeeds, restoring the cells it has; a rollback into a smaller world raises the **world's** `OutOfBoundsError`, not a `StoreError`, so the caller learns about it from the wrong component | The session's declared size is readable (`SessionInfo.world_width`, `world_height`) and the world's size is readable, so a caller can check. Measured: a 32 x 32 session rolled into a 512 x 512 world and into a 16 x 16 world both succeeded silently | the version naming phase 02 milestone 02 in [VERSIONS.md](../../plan/VERSIONS.md) |
| STO-06 | `ARCHIVE_FORMAT` is public in `history.__all__` and absent from the facade's `__all__`, while `ARCHIVE_VERSION` is exported | A consumer wants to check the format name it must write | The consumer reaches past the facade into a submodule for one constant, which is the coupling the facade exists to prevent | The name is reachable and documented in [interfaces.md](interfaces.md) §1; the fix is one name in one list | the version naming phase 02 milestone 02 in [VERSIONS.md](../../plan/VERSIONS.md) |
| STO-07 | An imported session is written with `archived=0`, so it appears in `sessions(include_archived=False)`; whether a caller should be offered the archive marking instead is not stated in the module's prose | A user imports an archive and then lists their sessions | An import that was meant to put a session away leaves it in the working list. The behaviour is deliberate — the test argues that "an imported archive is a session you can work on, not one that has been put away" — but the argument lives in a test comment rather than in the contract, so the next reader has to find it | The behaviour is measured and asserted ([interfaces.md](interfaces.md) §5, [data-flow.md](data-flow.md) §5.3, `test_an_archive_round_trips_into_a_fresh_store`). The decision to write down is whether `import_archive` should grow a flag or whether the listing is the right default | the version naming phase 02 milestone 02 in [VERSIONS.md](../../plan/VERSIONS.md), which owns the decision rather than the fix |
| STO-08 | A delta can be larger than the keyframe it descends from. Measured on a 30 percent chaotic fill, every delta exceeded the generation 0 keyframe | A dense chaotic population is recorded | Storage grows faster than a keyframe-per-interval scheme would, and every rollback still pays the replay cost of the larger deltas. The module's rationale assumes `born + died < population` and nothing checks it | The case is measured and stated ([performance.md](performance.md) §4) rather than averaged into the good case. Bounding `born + died` at the population in `record` is a candidate change in [performance.md](performance.md) §7 | the version naming phase 02 milestone 02 in [VERSIONS.md](../../plan/VERSIONS.md); the rule that bounds it is a decision and may belong in an ADR |
| STO-10 | `latest` transfers every row of the session, both blobs included, and sorts to take the first | A caller reaches for the newest node the long way | `O(n)` work and traffic for one row. Nothing on the recording path calls it — `record` reads the session's head by primary key — so recording is not quadratic, and the caller today is the `open` reply, once per archive. A future per-generation caller would pay it per generation | Measured and stated ([testing.md](testing.md) §7.3, [performance.md](performance.md) §5). The fix is one clause (`LIMIT 1`), listed in [performance.md](performance.md) §7 | the version naming phase 02 milestone 02 in [VERSIONS.md](../../plan/VERSIONS.md) |
| STO-12 | `Store` holds one connection and does not claim thread safety. Two threads sharing one `Store` can interleave statements on that connection | An embedder drives one store from two threads | A lost update or a driver error the module's vocabulary does not describe. Two **stores** on one file are a different case: the second writer now gets `StoreLocked` from `BEGIN IMMEDIATE` rather than the driver's raw error | The absence is stated in [interfaces.md](interfaces.md) §2.1 and [overview.md](overview.md); the module does not promise concurrency, and a protocol that hides the store behind one writer is the future direction | not scheduled; a multi-writer store is a different design with its own decision |
| STO-13 | A replay of a long chain builds a Python `set` of every live cell, so memory grows with the population rather than staying bounded | Rolling back a generation of a world with tens of millions of live cells | The rollback is correct and slow, and the process's memory grows to hold the whole live set as Python tuples | The keyframe interval bounds the number of deltas replayed, not the size of the set. The packed-key array the sparse world already exposes would be the bounded representation, and adopting it would change this module's internal storage | not scheduled; the measurement that would size it has not been taken ([performance.md](performance.md) §9) |
| STO-14 | A schema-2 session that changed its rule is migrated with its starting rule written onto **every** generation: schema 2 stored one rule per session and `set_rule` never updated it, so the change point is not recoverable from the old data | An old store is opened, and its timeline is read | The generations after a rule change are labelled with the rule the session started on, so a reader of the migrated history sees no change where one happened. It is the one thing the migration cannot know, and it is stated rather than hidden in a column default ([implementation.md](implementation.md) §3.6) | The migration writes the only surviving value and the uncertainty is documented; a session that never changed its rule migrates exactly. Sessions recorded from the version that stores per-generation rules do not have this at all | not scheduled; nothing can close it for data already written, because the evidence was never stored |
| STO-16 | A delete that cascades along a deep parent chain exceeds SQLite's trigger limit. `lifegame_generation.parent_id` is a self-referential `ON DELETE CASCADE`, and SQLite implements a cascade as an internal trigger, so the delete walks the chain one level per row. Measured after the migration was fixed: on a migrated 1300-node store, `DELETE FROM lifegame_session WHERE id = 10` still raises `too many levels of trigger recursion` | A feature that deletes a session, or any delete of a node that has descendants on a chain deeper than `SQLITE_MAX_TRIGGER_DEPTH` (1000 by default) | The declared cascade cannot complete, and the failure arrives as the driver's error rather than in this module's vocabulary. Nothing shipped asks for it today — the only delete is `truncate_after`, which removes nodes deepest-first and so never cascades — but the first session-deletion feature meets it immediately | The absence is stated in [interfaces.md](interfaces.md) §10, [data-flow.md](data-flow.md) §6 and [testing.md](testing.md) §6. The fix for the migration does not fix the mechanism: the limit is about the cascade, not about the drop that used to trigger it | not scheduled on its own; the version that adds session deletion meets it first, and [VERSIONS.md](../../plan/VERSIONS.md) owns which one that is |
| STO-18 | The rebuild's order is verified for SQLite only. MySQL's `foreign_key_violations()` answers `None`, because InnoDB has no statement that re-examines stored rows the way `PRAGMA foreign_key_check` does, and its DDL is not transactional, so a rebuild that fails part-way cannot roll back the way SQLite's does | A migration of a MySQL store, or a caller that treats the two backends as interchangeable | Two steps of the order — the pre-commit check and the rollback that protects the copy — have no MySQL form. A MySQL rebuild would commit a result nothing verified | The seam is explicit rather than silent: `None` means "not asked" and is kept distinct from `[]` meaning "asked and clean", so a caller cannot mistake the gap for a pass ([interfaces.md](interfaces.md) §1). This is the rebuild's share of STO-01, whose cause is that no MySQL server exists in this environment | the version that has a MySQL server to run against, see [VERSIONS.md](../../plan/VERSIONS.md) and [testing.md](testing.md) §8 |
| STO-20 | `foreign_keys` is a **per-connection** setting, not a property of the file. "Enforcement is on after a migration" therefore means two things and not a third: the migrating connection ended with the value read back as `1`, which is asserted, and every later `Store.open` applies the pragma again, which the connection-pragma cases decide. A bare `sqlite3` connection to the same file reads `0` until it sets the pragma itself | A reader or writer that opens the store file directly, without this module, and expects the declared constraints to fire | Rows naming a session or a parent that does not exist can be written on such a connection, and this module's later read then walks links that point at nothing | The pragma is applied on every connection the module opens and each value is read back by a test ([testing.md](testing.md) §7.2); the limitation is stated rather than implied, and it is why the rebuild's assertion is about the connection it changed rather than about the store | not scheduled; it is how SQLite defines the setting, and a store that needs enforcement against every connection would need a different guarantee than a pragma |

## 3. Record gaps found by this directory

An unresolved item without a home is a defect, so the ones this directory finds
are listed rather than left implicit. **It currently finds none open**: STO-19 was
a real consequence of the rebuild's refusal and is now closed by `salvage`, which
copies a damaged store, clears the dangling links and reports them without writing
to the source. What is closed is in §4, which also carries the crash this register
missed while it was open. Four things it checked and did **not** find are worth
recording, because a risks file that only ever grows is not being read:

| Item | Result |
|---|---|
| Whether a rollback can return a state that is not the one asked for | No. The defect that made this possible (STO in [testing.md](testing.md) §7.1) is closed, and the rule that closed it is stated as a prohibition in [responsibilities.md](responsibilities.md) §4 |
| Whether a failed import can leave a partial session | No. The write is one transaction and a test asserts the store is unchanged after a malformed line |
| Whether the register would have caught the migration crash | No. Opening a schema-2 store raised `too many levels of trigger recursion` on any history deeper than SQLite's trigger limit, which is the default path of the store rather than an edge, and the register did not carry it while it was open. It is closed and recorded in §4 as STO-15 |
| Whether an old store whose own links dangle can be opened | Not in place, and deliberately: the rebuild checks the result and refuses, which leaves the file untouched. The path forward is `salvage`, which repairs a copy and reports what it cleared; it closes STO-19 in §4 |

## 4. Closed since this register was written

Kept rather than deleted, because the reason each was open is the reason the test
that closed it exists. Each row names what was measured and where.

| Was | Why it was open | What closed it |
|---|---|---|
| STO-15: the schema 2 → 3 rebuild raised `too many levels of trigger recursion`, so a deep store could not be opened at all | `DROP TABLE` with foreign-key enforcement on performs an implicit `DELETE FROM`, and the self-referential `ON DELETE CASCADE` on `lifegame_generation.parent_id` walked the parent chain one level per row — so the depth of a store's history decided whether it opened. The threshold was measured rather than assumed: 1000 nodes migrate, 1001 fail. This register did not carry it while it was open, so it is written down here rather than dropped, and the cause is kept with it | The rebuild turns enforcement off outside any transaction and **reads the value back**, runs in one transaction, checks `PRAGMA foreign_key_check` before committing, rolls the whole thing back on any violation, and restores enforcement in a `finally`. The order is [implementation.md](implementation.md) §3.6; the cases are `test_a_version_two_store_deeper_than_the_trigger_limit_migrates`, `test_a_migrated_deep_store_still_records_and_replays` and `test_a_schema_two_store_whose_own_parent_links_dangle_is_refused_untouched`; the record is [testing.md](testing.md) §7.7. The mechanism that remains is STO-16 |
| STO-05: `StoreLocked` was declared, exported and never raised | The error vocabulary promised a branch no code path could take | `SqliteBackend.begin` translates the driver's lock and busy errors into `StoreLocked`, `test_a_second_writer_is_told_the_store_is_locked` forces the condition, and [interfaces.md](interfaces.md) §3 and [responsibilities.md](responsibilities.md) §3 say so |
| STO-09: the SQLite pragmas the schema declares were **not in force** | They were executed inside a transaction, where SQLite ignores `journal_mode` and `foreign_keys` silently, so the store ran on the rollback journal with foreign keys off while its own comment claimed write-ahead logging | The pragmas are applied on every connection, outside any transaction, and `test_the_sqlite_pragmas_actually_take_effect`, `test_the_pragmas_are_reapplied_on_every_connection` and `test_the_foreign_key_cascade_actually_deletes_the_history` read the effective values and the enforced cascade back. The defect record is kept in [testing.md](testing.md) §7.2 |
| STO-02 / STO-11: no migration path, and no version named one | A store written by an older schema could not be opened at all | `Store._migrate` reads a schema-1 or schema-2 store and rebuilds it as the current schema in one transaction, through one writer; the three cases are decided by [test_history.py](../../../tests/store/test_history.py). The uncertainty the migration cannot remove is STO-14, and the migration itself is [implementation.md](implementation.md) §3.6 |
| The `_now` coupling across a component boundary: `archive-format` imported a **private** function from `history-core` | A cross-component reach into a name its owner does not export, invisible in the import block of the component that permitted it | The timestamp helper lives in `schema-authority` as `schema.now`, and both components import it from there. The history is kept in [internal-components.md](internal-components.md) §2.1 |
| STO-17: `truncate_after` destroyed a sibling branch | The delete loop removed only the head's path, but `lifegame_generation.parent_id` is a self-referential `ON DELETE CASCADE`, so deleting a path node cascaded to every child it had — including a node that was never on the path and that the method's docstring promised to keep. Measured with nodes `[1,2,3,4,5]`, the working point's path `1 → 2 → 3 → 5` and node 4 a live sibling under node 2: `truncate_after(0)` left `[1]` | The call reads each surviving child's state before anything is deleted, clears its parent link and rewrites it as a keyframe in the same transaction as the deletes and the head update; the returned count excludes the kept branch. The case is `test_truncating_a_branch_keeps_a_sibling_it_never_named`, and the mechanism and the rejected alternatives are [implementation.md](implementation.md) §6 and §7. The decision the finding needed — clear the parent, refuse, or change the promise — was taken as the first, and [interfaces.md](interfaces.md) §2.4 states the resulting contract |
| STO-19: a schema-2 store whose own rows violated its keys could not be opened at all | The rebuild's check refused it, correctly, and left the file untouched, but offered its owner no next step; the decision it needed was between repairing, quarantining and partly importing | `salvage(source, target)` copies the file with `VACUUM INTO`, opens the copy with `repair_dangling=True`, clears the dangling links and reports the row ids, and leaves the source byte-identical. A cleared delta branch refuses a replay by name. The cases are `test_a_dangling_schema_two_store_is_salvaged_into_a_usable_copy` and `test_salvage_refuses_to_overwrite_its_target`; the mechanism is [implementation.md](implementation.md) §3.6 and the interface is [interfaces.md](interfaces.md) §2.1 |
