# world — risks

> This file owns the risks that are still open. Every entry names its trigger,
> its impact, its mitigation and the version that owns it; an unresolved risk
> without an owning version is a defect
> ([AI_DOCUMENTATION_GUIDE.md](../../AI_DOCUMENTATION_GUIDE.md) §5.8). Defects
> already found and fixed are recorded in [testing.md](testing.md) §6, not here.
> Version state is owned by [VERSIONS.md](../../plan/VERSIONS.md).

## 1. Open risks

| Id | Risk | Trigger | Impact | Mitigation | Owning version |
|---|---|---|---|---|---|
| WLD-01 | Neither shipped representation runs the design target when the population is **spread across it**. The tiled world's cost follows the number of non-empty tiles and not the number of live cells, so 43 million live cells spread over 65536 x 65536 at one percent per tile fill about 1,048,576 tiles: projected at the measured 8.5 microseconds per tile that is about 8.9 seconds per generation, against about 19.8 seconds for the sparse world. | A world is run at the target scale with a population that covers the world rather than sitting in one region. | The world can be represented, edited and stepped by hand, but a generation still takes seconds. The tiled representation closes the gap for a compact population, not for a diffuse one — the two cases differ by a factor of a hundred. | The same two shapes are measured and stated ([performance.md](performance.md) §6), not averaged away, and both projections are labelled as projections from a 1024 x 1024 ladder that has never been run at a larger area. What is missing is a rule that chooses by measured shape; no milestone declares one. | **unowned** — see §3 |
| WLD-04 | Mutation is linear in the representation's unit: `toggle` and `set_alive` move the tail of the sorted key array — linear in the live population for the sparse world, linear in the tile count for the tiled world. | A viewer sends many clicks in one frame, or clicks repeatedly at a high population. | UI latency that grows with the world, at a point where the user expects an immediate response. The tiled world is the better of the two here, because a click moves tiles rather than cells. | The locate step is `O(log n)` in both and only the tail moves. The cost is inferred from the bound and has not been measured, so it can be sized when a viewer makes it matter. | not scheduled; a viewer that batches clicks would make it worth measuring |
| WLD-05 | **Closed for this module; the residual is the store's.** A world cannot be persisted **by this module**, so a process that restarts without an external history loses it. Persistence now exists — the [store](../store/overview.md) module records generations as the cells that changed and restores any recorded generation — but it is a separate module with its own risks, and a caller that never drives it has no protection | The process exits, crashes, or is restarted by an operator, and nothing was recording | A session's world is gone; nothing can be resumed. For a large world this is the difference between a tool and a toy | This module supplies the two ends of the flow — `advance` for what changed, `restore` for a saved state — and keeps no format of its own, which is what leaves the format decision with the module that owns it ([store/risks.md](../store/risks.md) STO-01 and STO-11 are what remains) | closed for this module by the version that names phase 02 milestone 02 in [VERSIONS.md](../../plan/VERSIONS.md), which delivers the store |
| WLD-06 | The protocol's cost is measured for two commands and nothing else. | A large `frame` request, a high `run` rate, or a `set` over many cells. | The interactive path can be sized for clicking and for polling a viewport, and not for anything else. | `state` and a 1024 x 1024 `frame` are measured under both representations ([performance.md](performance.md) §7); the rest is listed as unmeasured in §9 rather than estimated. | **unowned** — see §3 |
| WLD-07 | The `internal` error code can present a real bug as a protocol-level refusal. | Any unexpected exception inside a handler. | A consumer that treats `internal` as routine keeps going on a core that may be in a state it does not understand. | The error carries the exception type and message; the module guarantees the world is never left partially updated ([data-flow.md](data-flow.md) §5.1); the contract tells a consumer to re-read `state` after an `internal` error ([data-flow.md](data-flow.md) §5.3). No test triggers the path ([testing.md](testing.md) §8). | **unowned** — see §3 |
| WLD-08 | One `Bridge` serves one world on one thread; its write lock serialises output only. | An embedder drives one world from two threads, or runs two bridges over one world. | A lost update: every mutation rebinds the storage array, so two concurrent mutations can lose one of the two. | The module does not promise concurrency. The protocol is the supported interface, it is single-client, and the service is documented as a consumer. This risk exists so that an embedder who reaches for the library directly meets the constraint before the bug. | not scheduled; a multi-client core is a different design with its own decision |
| WLD-09 | The representation is chosen by the caller and defaults to `sparse`, which is the **slower** of the two for a clustered population. | A caller runs a clustered world without passing `--representation tiled`. | The world runs correctly and up to fifty-five times slower than it would have, with nothing in the reply saying so. A wrong default is silent, unlike a wrong result. | The choice is an explicit argument with a documented default ([interfaces.md](interfaces.md) §4.10), and it can also be made from a running core without losing the world; the frontier is measured over two shapes, so the trade-off is visible rather than buried. The default is `sparse` on purpose: an interactive session produces the scattered shape. Choosing from the interface does not help a caller that never chooses, so what is missing is dispatch by measured shape, and no milestone declares one. | **unowned** — see §3 |
| WLD-10 | The tiled world's advantage reverses on reads: it wins on stepping and loses on querying, because a query unpacks the bit store. | A viewer polls `frame`, or a caller polls `state`, while a tiled world is running. | The representation chosen for its step can be several times slower for the workload the viewer actually generates. | Measured under both representations at 260,000 live cells ([performance.md](performance.md) §7): `state` 9.41 ms tiled against 1.27 ms sparse, a 1024 x 1024 `frame` 12.00 ms tiled against 3.75 ms sparse. The measurement exists so the choice is made against both halves of the workload rather than one. What is missing is a rule that weighs them, and no milestone declares one. | **unowned** — see §3 |
| WLD-11 | Three names this module exports are a contract with the [store](../store/overview.md) module, which does not import this module and therefore cannot be broken by a compiler: `advance`, `restore`, and every field of `Change`. | A field of `Change` is renamed or removed, or `restore` changes what it sets | The history layer breaks without a line of its code changing: a stored delta would be read from the wrong field, or a restored generation would come back with the wrong counter. Nothing in either module's test suite would necessarily fail first | All three are in the compatibility policy ([interfaces.md](interfaces.md) §8) rather than treated as internal detail, and the coupling is stated from both sides ([responsibilities.md](responsibilities.md) §2.6 and [store/responsibilities.md](../store/responsibilities.md) §2.1). **Partly closed:** the protocol tests now drive a real store through all three — a recorded core's timeline, a rollback, and an archive round trip ([testing.md](testing.md) §4) — so a rename in any of them fails here. What remains is the other direction: the store's own suite still does not exercise a protocol-driven world | **unowned** — see §3 |
| WLD-12 | A recorded timeline does not survive a representation switch. Switching starts a new core process, and therefore a new store session, so the timeline restarts at the generation that was carried over and everything before it stays in the old session's rows. | A client switches representation and then asks for `history` | The person sees a timeline that appears to have lost its past, and the earlier generations are still on disk but not reachable from the running core. This is current semantics rather than a defect, and it is only a defect if a client presents the timeline as continuous | The switch is a client's decision and the protocol never claims continuity: `history` reports the session it is answering for, so a client can tell that the session changed. Told apart from a rollback, which does **not** start a session | the version naming phase 03 milestone 01 in [VERSIONS.md](../../plan/VERSIONS.md), where timeline continuity across a switch is declared |
| WLD-13 | **The refusal of a non-local rule is an outward behaviour change.** `SparseWorld` and `TiledWorld` accept a rule whose birth set contains zero no more: the constructor and `set_rule` raise `ValueError`, and the protocol answers `bad_rule` ([interfaces.md](interfaces.md) §3.1) | A caller or a stored script passes a `B0`-class rule, or a person types one into a client that sends it | A caller that relied on the old behaviour breaks **loudly** at the request instead of receiving a wrong number, and a caller that genuinely wants such a rule has to use `DenseWorld`, which cannot be allocated at the design scale | The old behaviour was not a feature: it was a silently wrong answer, measured at 39 live cells where 63 are correct for an 8 x 8 world with one live cell under `B012345678/S`. The refusal names the rule, the reason and the representation that can run it, and the protocol reports it as `bad_rule` rather than as `internal`, so a consumer can branch on it. The change is covered by a test that asserts both refusals and that the oracle still runs the rule ([testing.md](testing.md) §1) | the version naming phase 03 milestone 05 in [VERSIONS.md](../../plan/VERSIONS.md), which took the change and records it as one |
| WLD-14 | **The rule space is covered by a bound that is wider than the assertion, and by behavioural evidence for fourteen rules.** One set alone compiles to at most sixteen word operations, asserted for all 512 single sets; over all 262144 `(birth, survive)` pairs the measured maximum is **24**, and 124,240 pairs exceed sixteen. Separately, only the fourteen rules in [test_rule_equivalence.py](../../../tests/world/test_rule_equivalence.py) have been run against the dense oracle | A rule outside the fourteen is used, or the compiler is changed in a way that lets a pair grow without any single set growing | A regression in a pair's plan size would pass the existing test, and a rule that mis-selects a count would be caught only if it belongs to the fourteen. The step remains correct as far as anything measured says, and the bound that is documented as a guarantee is not the bound the test asserts | The single-set bound is asserted exhaustively and is what the complexity claim uses; the fourteen rules include the shapes that break the network differently (a set spanning every group, no survival, no birth, both sets equal, and the count-of-eight edges). What is missing is an assertion over the pair space and a wider oracle sweep. The docstrings of `_SelectionNetwork` and of the bound test claim the pair space was compiled and never exceeded sixteen, which the measurement contradicts | **unowned** — see §3 |
| WLD-15 | **The compiled plan is interpreted in Python.** A step walks the plan step by step, and each step is a numpy traversal of an `(M, 64)` array | A rule with a large plan runs at a scale where the rule application is a measurable part of the step | The rule's cost carries an interpreter overhead the geometry does not have: at 256 tiles the plan walk alone is about 17 us per call, and the three-operation Conway plan is *slower* than the seven-operation expression it replaced (79.5 us against 62.9 us, [performance.md](performance.md) §5.9) | Measured and stated rather than hidden, and it is inside the 17 to 20 percent a whole step grows by, because the geometry around it dominates. Removing it means compiling a plan into a closure or generated code, which is a new mechanism with its own failure modes, and it was not built | **unowned** — see §3 |
| WLD-16 | **The carry-save (3:2) adder tree is an unmeasured candidate with an estimate attached.** The count chain is 64 word operations per tile and the largest single part of a step, and a 3:2 tree is estimated to bring it to about 34 | Someone reads the estimate as a result and plans against it, or the frontier is compared with a build that has the tree in it | A projected improvement is quoted as a measurement, or a comparison is made across two different count implementations and attributed to the rule | Recorded as a candidate and as **not adopted**, with the reason: it would move an already-recorded frontier and confound every comparison against it, and it needs its own correctness proof ([performance.md](performance.md) §10) | **unowned** — see §3 |

## 2. Phase risks that touch this module

Summarised and linked, not restated: the phase register owns these, and
[phase-02-simulation-core/risks.md](../../plan/phase-02-simulation-core/risks.md)
is their home.

| Phase id | Subject | Relation to this module |
|---|---|---|
| R10 | The shipped representation loses to dense above about four percent density, and the target admits far higher densities | Partly overtaken. The module now ships the representation R10 asked for, and the measurement shows it winning by up to fifty-five times on a clustered population; what R10 does not yet say is that the win depends on the population being clustered (WLD-01) and that the faster stepper is not the faster reader (WLD-10). The phase register owns the phase-level statement and needs to follow |
| R11 | numpy puts compiled code in the runtime path | The module's only third-party dependency. [ADR 0006](../../adr/simulation-core/0006-numpy-is-the-vectorised-substrate.md) records the boundary; the dependency is stated in [overview.md](overview.md) and [implementation.md](implementation.md) §4. The tiled representation makes it a stronger dependency than before: the bit-parallel step has no non-numpy expression |
| R14 | The protocol has one implementation and no compatibility test against an older consumer | The protocol is defined here ([interfaces.md](interfaces.md) §4) and its version is carried in `hello`; the gap is that nothing tests an older consumer against a newer core. `--representation`, the `export`/`import` pair and now `set_rule` were each added without changing `PROTOCOL_VERSION`, which is defensible only while a consumer that ignores them still works — an unknown command is answered with `unknown_command` and the process survives, and that is not tested either. `set_rule` adds a second question the version number does not answer: a consumer that knows the command but not the `bad_rule` code has to treat an unknown code as it treats any other |
| R15 | The world is bounded and does not wrap, which a user may read as a bug | Recorded as a decision, not a risk, in [ADR 0008](../../adr/simulation-core/0008-the-world-is-bounded-and-does-not-wrap.md); the phase register lists it because a user can still be surprised by it. The tiled world makes it more visible, because a partial tile at the edge is a place where padding and bounds could be confused — [test_tiled.py](../../../tests/world/test_tiled.py) is what holds that line |

## 3. Record gaps found by this directory

An unresolved item without a home is a defect, so the ones this directory finds
are listed rather than left implicit. The open items below are decisions for the
owner of version state; the one with a correctness edge rather than only a
performance one is WLD-14, where the documented compile-time bound is not the
bound the test asserts.

| Item | State |
|---|---|
| **WLD-14, WLD-15 and WLD-16 are new, and none has an owning version.** They were opened with the rule work and each is a decision about how much evidence is enough: whether the compile-time bound should be asserted over all `(birth, survive)` pairs rather than over single sets, whether the plan's Python interpretation is worth compiling away, and whether the carry-save candidate should be built and measured. | **Open.** Each needs a home in [../../plan/VERSIONS.md](../../plan/VERSIONS.md), or a recorded decision to leave it open. WLD-14 is the one with a correctness edge rather than only a performance one: the documented bound and the asserted bound are not the same bound. |
| **The milestone-02 owners in §1 and §4 are stale.** WLD-01, WLD-06, WLD-07, WLD-09 and WLD-10 named "the version naming phase 02 milestone 02" as their owner, and that version was delivered without any of them: it delivered the history layer, the representation **choosable by a person**, the push transport and the browser coverage, and none of those is shape-aware dispatch, a protocol compatibility case, an `internal`-path test, or a measurement of the remaining commands. Version state is not this directory's to set, so the cells read **unowned** and the items are reported here rather than reassigned to a milestone that has not accepted them. | **Open.** Each needs a home in [../../plan/VERSIONS.md](../../plan/VERSIONS.md) and in a milestone register. Resolving it means deciding whether phase 03 takes them or whether they are deliberately dropped; leaving the cells pointing at a delivered version would make the register read as if the work were done. |
| WLD-01 and WLD-09 were reported here as having no owning version, because the version that names phase 02 milestone 01 declares the tiled representation, the two-shape frontier and viewer presentation work, and none of those is dispatch. | Closed at the time: the version naming phase 02 milestone 02 declared representation selection, so both were assigned to it. **Reopened by the row above**, which records that the same version shipped selection from the interface rather than from measurement. |

## 4. Open questions

Each names the version that will answer it. Every owner below that reads
"the version that names phase 02 milestone 02" is **stale for the same reason as
the first row of §3**: that version was delivered without these items, so each
question is unowned until the version-state owner places it. They are left
readable rather than rewritten one by one, because the decision is not this
directory's.

| Question | Why it matters | Owner |
|---|---|---|
| Where exactly does the tiled crossover fall, between 400 and 4,000 live cells on a clustered population? | Two runs bound it but do not pin it: at 400 the sparse world is still ahead, and by 4,000 the tiled world is several times ahead. A dispatcher would need the rung | **unowned** — see §3 |
| Which quantity should dispatch on: non-empty tiles, live cells, or the ratio between them? | The measurement says the tiled cost follows non-empty tiles and the sparse cost follows live cells, so the deciding number is their ratio. That ratio is computable in both representations, but which threshold to use is a decision, not a measurement | the version that names phase 02 milestone 02, once dispatch is in a version's scope |
| Do the per-cell and per-tile constants hold at a world larger than 1024 x 1024? | Every figure here comes from one area. The sparse step's cost should not depend on the world's area and the tiled step's should not either, but neither claim is tested, and §6 of [performance.md](performance.md) projects from them | the version that owns M02 in [VERSIONS.md](../../plan/VERSIONS.md) |
| Is the tiled world's query cost reducible without giving up its step cost? | A query unpacks 64 cells per word. A cached decode, or a frame path that stays in the bit domain, would change WLD-10 from a trade-off into a non-issue — but the current frame path already stays in the bit domain for `bits` frames, so where the 12 ms goes is not yet decomposed | the version that names phase 02 milestone 02 |
| Would a hash-based sparse set be faster than the sort, if numpy gains a vectorised hash map? | The `log` factor is the whole asymptotic argument against the sparse family. If a vectorised hash existed on the substrate, the comparison would have to be re-run rather than assumed | not scheduled; a substrate change would reopen it |
| What should the admission floor be now that a representation can meet one? | A floor is only meaningful against a representation that can meet it. With the tiled world measured, a floor is now definable — for the clustered shape at least, and that qualification is the point | the version that names phase 02 milestone 02 in [VERSIONS.md](../../plan/VERSIONS.md) |
| Is a batched mutation entry point worth adding for the viewer? | Clicks are `O(n)` each in both representations; a batch could pay the memory move once. Whether it matters depends on a viewer that does not exist yet | the version that names phase 02 milestone 02, once the viewer's transport is decided |
| Should the protocol carry a `changed` count for `set` per cell, or is the total enough? | The reply reports how many cells the call changed, not which. A viewer that animates a batch would want the detail | the version that names phase 02 milestone 02 |
| Is 8 bytes per live cell the true peak for the sparse world, and what is the tiled world's? | A sparse step holds a candidate array of up to `9L` entries, and a tiled step holds several `(M, 64)` arrays. At the target's densities those are the difference between a machine that copes and one that does not | the version that owns M02 in [VERSIONS.md](../../plan/VERSIONS.md) |
| Does `advance(record=True)` change the cost of a step measurably, and at what population? | The claim is that naming the cells costs a comparison of two masks rather than a rescan, so the cost should be a small fraction of a step. It has not been measured on either representation, and a caller that records every generation pays it every generation | the version that names phase 02 milestone 02, if a caller records at rate |
| Should the compile-time bound be asserted over all `(birth, survive)` pairs, or is one set at a time enough? | The single-set assertion is exhaustive over 512 masks and is what the complexity claim uses, but the two sets share only part of their work, so the pair maximum is 24 and not 16. Asserting the pair space is cheap and would turn a documented bound into a tested one (WLD-14) | **unowned** — see §3 |
| Is a model of a plan's cost worth building, given that the cost is not monotone in the plan size? | §5.9 of [performance.md](performance.md) shows an 11-operation plan costing more than a 13-operation one, so the plan size is a bound and not a predictor. A model would have to price the distinct arrays a plan materialises, and nothing yet needs the number | **unowned** — see §3 |
| Should the count chain be rebuilt as a carry-save (3:2) tree? | It is the largest single part of a step and the only candidate with a large projected win, but it would move the recorded frontier and needs its own correctness proof. Adopting it is a decision about evidence, not only about speed (WLD-16) | **unowned** — see §3 |
