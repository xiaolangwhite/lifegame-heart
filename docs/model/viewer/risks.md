# viewer — risks

> This file owns the risks that are **still open**, each with a trigger, an
> impact, a mitigation and the version that owns it
> ([AI_DOCUMENTATION_GUIDE.md](../../AI_DOCUMENTATION_GUIDE.md) §5.8). Defects
> found and fixed inside the current version are recorded in
> [testing.md](testing.md) §7, not here. Version state is owned by
> [VERSIONS.md](../../plan/VERSIONS.md).

## 1. Open risks

| Id | Risk | Trigger | Impact | Mitigation | Owning version |
|---|---|---|---|---|---|
| VWR-01 | The service has no authentication and edits the world on request | An operator passes a non-loopback `--host`, or another local process learns the port | Anyone who can reach the port can toggle, clear, step, roll back and switch the representation of the world, and can cause an archive to be written into `data/`. There is no audit trail | The default bind is `127.0.0.1`, the archive name is confined to one directory and cannot name a path, and the risk is documented rather than assumed away. Authentication belongs with the session concept, not with a transport that has no sessions | phase 03, named in [ADR 0007](../../adr/service-and-api/0007-viewer-service-delivered-in-phase-02.md) |
| VWR-03 | The restart policy is exercised against a core that exits, not against one that hangs or dies mid-request | A core that stops reading its input, or a request in flight when the child dies | A hang is bounded only by the 30-second request timeout, so the page can appear frozen for that long; a death mid-request rejects the pending map correctly, which is the covered half | The per-request timeout and the crash limit bound both cases. A hang-until-timeout test would need a deliberately mute child. The push transport adds a second path into the same bridge, so a hang now stalls a stream as well as a request | not scheduled; the change that takes it up would add a mute-child fixture |
| VWR-05 | The `cells` path has no payload bound. `MAX_FRAME_CELLS` bounds the `bits` allocation; it does not bound eight bytes per live cell | A client requests a large rectangle over a dense world. The admission rule admits it whenever `population * 64 <= area`, which for the whole world holds up to about 67 million live cells | A response of up to a few hundred megabytes, and a browser that would try to build that many coordinate pairs. The page is bounded in practice — its zoom rule clamps once the population passes `MAX_FRAME_CELLS / 64`, about 262,000, so the page's largest whole-world request is about 2 MiB — but the API is reachable without the page | The page's own zoom bound is the practical mitigation. A payload or live-count cap on the API would be a second rule, and it is not taken here | not scheduled; the version that takes up the payload question in §3 |
| VWR-07 | The running world does not survive a core restart, even though a history store now exists | The core exits and the bridge restarts it, or the operator stops the service | The world is lost from memory and the page's population readout falls to zero. The *recorded* generations survive in `data/history.db`, so the loss is recoverable by rolling back — but nothing does that automatically, and a restart is not followed by a restore | The `503` path is explicit, the readout is honest, and the history routes make recovery a request rather than a lost session. Whether a restart should automatically roll back to the last recorded generation is a product decision, recorded as an open question in §3 | the version that decides whether a restart restores; persistence itself is delivered |
| VWR-09 | `clearStored` has no caller in the page | Nothing, until someone reads the module and assumes the feature exists | It is the only way back to "follow the system" once a theme has been chosen, and there is no control for it. A tested-but-uncalled export is either a missing feature or dead code, and neither is stated as such by the code alone | The function is tested and its purpose is documented in [interfaces.md](interfaces.md) §6.3. Adding a control is a product decision, recorded as an open question in §3 | not scheduled; the change that decides for or against the control |
| VWR-10 | The synthetic browser records the page's drawing calls but does not rasterise them, so nothing checks what the page looks like | A change that is arithmetically right and visually wrong: a stroke that blurs at a fractional ratio, two palettes that are hard to tell apart, a grid that is too heavy at four device pixels | A page that passes every test and is unpleasant or hard to read. The arithmetic that decides line width and centre *is* asserted, so the likely failure is appearance rather than geometry | The device-pixel geometry is computed and tested as arithmetic, and the contrast ratios are computed from the stylesheet and recorded in [performance.md](performance.md) §2.1. What remains is judgement | not scheduled; a headless browser would close it, and the phase has none |
| VWR-11 | The stream's 15-second heartbeat is never waited out by any test | A heartbeat that never fires, or one whose timer keeps the process alive | An idle connection dropped by a proxy or a firewall, which loopback cannot reproduce; or a service that will not exit | The timer is created with `unref()`, so it cannot be the reason the process stays alive, and a suite case asserts that a server with an open stream still exits. The interval itself is unverified | not scheduled; a case that waits fifteen seconds would dominate the suite, so it belongs with a fake-timer harness |
| VWR-12 | The hub's behaviour when a client's **first** frame never arrives, and what a second client sees while the first is stalled, are untested | A core that answers `hello` and then hangs on the first `frame`; or two subscribers where one is slow | One subscriber can be left with a `hello` and no picture, and the other's frames are serialised behind the stalled one, because the bridge issues one request at a time | Coalescing bounds the work per client rather than the work across clients. The request timeout bounds the stall at 30 seconds and turns it into an `error` event | not scheduled; the version that takes up multi-client behaviour in §3 |
| VWR-13 | A representation switch round-trips the whole live set through the service, and its cost at scale is unmeasured | A switch on a world holding millions of live cells | A visible pause with no progress indication beyond the control being disabled; the `503 switch_in_progress` window is as long as the export, the restart and the import together | The switch is refused rather than queued if one is already running, so pauses cannot accumulate. [performance.md](performance.md) §7 records the cost as unmeasured rather than estimating it | not scheduled; a measurement at scale is what it needs, and the frozen ladder is in [PERFORMANCE_ACCEPTANCE.md](../../plan/PERFORMANCE_ACCEPTANCE.md) |
| VWR-14 | One whole-suite run failed and was not reproduced: 41.21 s against a normal 4.0 s, with an `ERR_ASSERTION` of `actual: 0`, `expected: 1` and the failing case unnamed | A machine under contention, which is the normal state of the machine these were measured on — the suites spawn real Node and Python processes | An intermittent red gate. The gate is what tells a person whether a change is safe, so a gate that fails one run in fourteen is worse than one that is merely slow | Every subsequent run on record is green, and the candidate assertions are named in [testing.md](testing.md) §5.7. Every one of them waits on a scheduled continuation, so the shape of the failure is a continuation that had not run yet | not scheduled; the case has to be identified before it can be given an owner |
| VWR-15 | The stylesheet audit reads the stylesheet and the markup as **text**; it cannot evaluate a selector, so it cannot prove a rule matches anything at run time | A rule whose class or id exists but whose combination never matches — for example a descendant selector that names two tokens that never nest | A style that is written, reviewed, audited and never applied. The class of defect is real and has now been observed twice: the panel's three states were completely unstyled in the browser after the markup renamed the element the rules hung off, and the audit passed every case while it was true | The audit was strengthened from "the token appears somewhere in the file" to "the class appears where a class is **borne**" (`class=`, `className=`, `classList.add\|remove\|toggle`), and a case now asserts that a `[data-panel]` rule's subject class is on the element that really carries `data-panel`. That is strictly stronger and it is what found the dead `.stage` rules. It still does not evaluate a selector, so specificity, ordering and an overriding declaration remain invisible | not scheduled; evaluating selectors needs a browser or a CSS engine |
| VWR-16 | The page offers two languages and no more, and nothing checks a language that reads right to left | A third language is added, or the page is shown to a reader of Arabic, Hebrew or Persian | A language could be added to the catalogue and appear, while the layout — a toolbar row, the readouts, the timeline — was never designed for mirrored text | The toolbar's labels and buttons carry a minimum inline size precisely so that a wider or narrower language cannot shift the controls, which is the layout risk that was foreseeable from the two languages in hand. Direction is not addressed at all, and that is why this is a risk rather than a note | not scheduled; the change that adds a third language or any right-to-left language |
| VWR-17 | A core process that outlives the service keeps the history store open, so the store's three files cannot be deleted and the next run inherits what looks like a random failure | The service is killed rather than closed, or a test's teardown deletes the store before the child has exited | A locked `history.db`, `history.db-wal` and `history.db-shm`; the next start either fails to write or silently continues the previous session. Because the symptom is a file that will not delete, it presents as an intermittent failure rather than as a lifecycle bug | **Observed, not theorised:** after an end-to-end run a node process and two cores were still alive fifteen minutes later holding the store and its sidecars, and a forced kill from an agent's shell reported success without taking effect. Two things now stand against it. `scripts/viewer.ps1` is the supported way to run the service: it collects the descendants **before** killing anything, reaps the tree, then verifies that nothing was left and exits non-zero if something was, and it refuses to start while a core from an earlier run is alive unless explicitly told to reap it. And the suite stops the core explicitly before deleting, retries, and deletes all three files ([testing.md](testing.md) §7.8). Neither makes a core give up the store when its parent disappears, which is what would actually close this | the version that takes up core lifecycle and shutdown |
| VWR-18 | The tree's window cuts from the **beginning**, so in a long history the oldest rows — and with them a branch's root — can be hidden entirely | A history with more generations than the window holds, which a running world reaches in well under a minute at the default tick rate | A person sees a subtree with no visible trunk: a row whose parent is not on screen is drawn as a root, so two different branches can look like two unrelated histories. Nothing is lost from the store and a control widens the window, but the view can mislead before that | Indentation is rebased on the shallowest row still shown, so a window never renders as a staircase that drifts off the panel, and a row whose parent is missing is deliberately treated as a root rather than dropped. The better answer — folding a branch the way a file tree does, so a branch is one row that opens — is not implemented | not scheduled; the change that takes up folding |
| VWR-19 | The full-width panel state combined with the tree has been walked by hand and is asserted by nothing | A change to either the panel's states or the tree's rendering | The two features are each tested and their combination is not: in the full-width state the canvas is hidden, so a defect that appears only when the tree is given the whole width — a row that overflows, a branch letter that is clipped — would pass every gate | Each half is asserted: the panel suite decides the state, and the page suite asserts the stage's attribute and the tree's rows. What is unasserted is the layout they produce together, which is VWR-10's territory | not scheduled; it needs a browser or a layout engine |
| VWR-20 | The two-finger gesture is driven by a synthetic pointer sequence, which is not what a real touchscreen produces | A real tablet, where a finger's events arrive at a device-dependent rate, coordinates are fractional, and a third finger or a palm can land mid-gesture | The arithmetic and the state transitions are asserted, but the *sequence* a digitiser emits — jitter, a repeated coordinate, three simultaneous fingers — is not reproduced. A third finger in particular is a state the code handles by arithmetic that nothing drives | The gesture logic is pure and its properties are asserted as equalities, so the risk is in the sampling rather than in the decision. A real device or a recorded pointer trace is the only thing that closes it | not scheduled; it needs a real touchscreen or a recorded trace |
| VWR-21 | **This risk has now been realised, and the first browser session is what realised it.** No browser has ever run this interface, and the module allows no dependency that could provide one, so nothing about what the stylesheet *does* has been observed | A change to the tree, the preview or the split layout that is arithmetically right and visually wrong. The four defects recorded in [testing.md](testing.md) §7.13 all fired while the suite was green | The interface can pass all 292 cases and every gate and still be unusable, which is what happened twice over. Before: rows drew on top of one another, a row filled the whole page, opening one row's detail pushed every row below it down, and the rows did not look like a tree at all. Then, in the first session a person spent with the interface: a preview that painted black after a refresh, a generation that could not be selected by clicking it, a horizontal scrollbar that overlapped the newest generation so that the two flickered against each other, and an opaque element covering part of a label. **Two of those four, the flicker and the overlap, are layout self-feedback and stacking — exactly the classes the assertions below cannot reach, by construction** | What replaced the earlier four defects is asserted as a **model** rather than as a layout, and the distinction is the risk. A row's height and its connector geometry are checked by counting in-flow children against the track count read out of `style.css`, and by asserting the `position: absolute` rules that take the overlay and the gutter out of the flow. That is a reading of two files as text: it does not lay anything out, and it does not rasterise. Whether a connector actually meets the row above it, what a real line height does to a row, how the overlay's transition looks, whether the two columns survive a narrow window, and which of the two palettes is legible, are all unverified. A scrollbar that appears on hover and shifts the pointer off the element that caused it is a feedback loop through the layout engine; no amount of reading two files as text will show it | the four defects this session found are fixed by the version that follows this one, which reproduced each of them in a browser and measured it before changing anything: a canvas that was never painted and composed black because it was opaque, a pointer capture taken on the list so the row's click never ran, an overlay that widened the container it is scrolled in and so made a scrollbar appear under the pointer, and the same overlay drawing an opaque box twenty pixels wide over a label. **What the fix does not change is this risk itself**, and it has grown a second edge: the browser probe that found all four lives in a gitignored temporary directory, so a clean checkout has no way to repeat the measurement, and the interface is back to being observable only by a person |
| VWR-22 | The shell publishes a context object and a page module reads fields out of it, and nothing checks its shape | The shell stops publishing a field a page reads, or renames it | A page fails where it reads the missing field. That is a thrown error rather than a quiet blank — which is better than the alternative — but it is a run-time failure on a page a person had to open, in a module whose whole test strategy is to catch that earlier | The two event names come from one module, so the two halves of the handshake cannot be spelled two ways, and every page case that connects a module would fail if the handshake itself broke. What is unchecked is the *contents*: a field removed from the context is caught by whichever page case reads it, and by no contract case | the change that adds a page module, because that is when the context's shape is next re-argued |
| VWR-23 | A path nobody serves answers a JSON error envelope with `404`, including a trailing slash and the address the interface used before it became three pages | A person types `/world/` or follows a bookmark to `/index.html` | A wall of JSON where a person expected a page. It is a correct answer to a machine and an unhelpful one to a reader, and the routes that *do* exist are one edit away | The status code is right and the route table is the only place a path is declared, so the fix is presentational: a `404` that renders the layout with a short message. Not doing it keeps the error envelope uniform across every route | not scheduled; a product decision about how much the error page should say |
| VWR-24 | **The specification of the default view is ambiguous.** "The span is the canvas width over sixty" and "the view is exactly sixty cells across" cannot both hold, and both were on the table | A change made by someone who read the second form: a constant, a clamp, or a test asserting a fixed count | The page would open with a view that depends on the window it is in, or a zoom floor and ceiling that only agree at one window size — and the disagreement would be invisible in a screenshot of one machine | The arithmetic was chosen and confirmed by the person who specified it: the span is `cssWidth / 60`, and the *scale* is what is fixed. The record is a decision, not a preference: it is the default in force, and it is switchable in one place — `DEFAULT_PIXELS_PER_CELL` in [public/viewport.mjs](../../../src/viewer/public/viewport.mjs) — if it is ever revisited | the change that re-argues the opening scale |

Worse, the *page* half of the path is only exercised against a synthetic reply: the sentence beside the canvas, the fact that the preview is still useful at all, and the latency of the real reply have not been observed | The cap and the sentence are declared once in [public/shared.mjs](../../../src/viewer/public/shared.mjs), so the two cannot disagree about *when* it applies; what is unvalidated is the number and the wording. It is not closed as a *class*: nothing checks the stub against the core's encoder, and a future change to either could reopen it. The independent decoder in [bridge.test.mjs](../../../src/viewer/tests/bridge.test.mjs) is the closest thing to a cross-check, and it covers frames the suite does not build | the change that generates the stub's payloads from the core's own encoder |

What is missing is the negative assertion; a case that reads both modules and fails on a reintroduced name would close it, and it is cheap | the change that takes up the negative assertion |

`VWR-02`, `VWR-04`, `VWR-06`, `VWR-08`, `VWR-28` and `VWR-34` were retired, and
the identifiers are not reused:

* **VWR-02** — no test case lay in the band where the superseded and the corrected
  admission rules disagree, and the case now does. Its history is in
  [testing.md](testing.md) §7.1.
* **VWR-04** — "`MAX_FRAME_CELLS` is declared twice and the two can drift". It is
  declared **once**, in [public/shared.mjs](../../../src/viewer/public/shared.mjs),
  which the service imports by relative path and the browser loads over
  `/static/shared.mjs`, and the rule that uses it is in the same file. The
  service-side default rectangle that shared the file is **gone rather than
  moved**, so there is nothing left for a second declaration to disagree with
  ([implementation.md](implementation.md) §3.10). The plan's `shared-bounds`
  component predicted a shared module or a published value and chose the first
  ([internal-components.md](internal-components.md) §4).
* **VWR-06** — "the page's rendering and gestures have no automated test". The
  synthetic browser and the page suite are the answer that risk asked for: the
  real `app.js` is executed, its two render paths are asserted on the calls they
  make, and its gestures are driven. What the harness cannot do is rasterise,
  which is a narrower risk of its own, `VWR-10`.
* **VWR-08** — "the canvas palette cache is the one connection no test executes".
  It was the seam where the `paintBits` defect hid. The page suite draws a frame
  of each encoding, so the cache that is filled is the cache that is read and the
  pixels are asserted.
* **VWR-28** — "the rule editor's button is inert on a fresh load". It was fixed
  inside the version that delivered the editor: the field is filled from the
  handshake rule the first time the rule arrives, and never again once the person
  has typed. The browser probe that found it passes against the same press now,
  and the defect record is [testing.md](testing.md) §7.15.
* **VWR-34** — "the remembered view is shared across sessions". It is now stored
  per session, and sharing is explicit through a `?focus=x,y` link; the focus
  suite asserts both properties ([testing.md](testing.md) §1).

## 2. What bounds the risks above

Three properties of the module keep most of §1 inside a local development
surface:

* The service writes no file itself, and the files it causes to exist are both
  named by the operator: the history store, whose default is `data/history.db`
  inside the repository, and archive exports, which are confined to the same
  directory and named rather than pathed. VWR-17 is the one risk that follows from
  a file existing at all, and it is about the core's lifetime rather than about
  what is written.
* It binds loopback by default and has no session, so the blast radius of
  VWR-01 is the machine the operator is sitting at.
* The server's rule is the guard and the page's rule is the same rule imported
  from the same module, so a request can no longer be admitted on one side and
  refused on the other; VWR-04 is closed rather than bounded.

The remaining risks have moved to the edges of verification rather than of
authority. VWR-10, VWR-11, VWR-12, VWR-14, VWR-15, VWR-16, VWR-21, VWR-22 and
VWR-26 are all cases where something real runs and nothing observes it: a
rasteriser, a fifteen-second timer, a stalled first frame, a shared machine, a CSS
engine, a text direction, a browser, the shape of an object handed between two
modules, and the agreement between a test stub and the encoder it stands in for.
VWR-24, VWR-25, VWR-27 and VWR-29 are the four that are about a **decision**
rather than an observation: an ambiguous specification that was settled and
recorded, a cap whose number has never been measured at the scale it applies to,
a rule whose absence nothing asserts, and two grammars kept in step by tests
rather than by one source. That is the honest shape of the coverage — the *logic*
is asserted as equalities, the *wiring* is executed, and what is left is the
environment the tests cannot provide. VWR-21 is the one to weigh most heavily,
because it is the risk this interface has already been burnt by three times: a
page can be green in every suite and blank in the browser, and the fourth time it
was four defects drawn on top of one another while 255 cases passed.

**VWR-28 was the fifth time, and it is the first one the probe found rather than a
person.** The rule editor's button was inert on a fresh load while every suite was
green, and the only thing that noticed was a real browser pressing it and finding
no request ([testing.md](testing.md) §5.10). It was fixed inside the version that
delivered the editor, and the same press now issues the request; the failure stays
in the record because it is the reason the probe exists. The probe exercises
declared interactions rather than only loading pages, and the check that caught it
is exactly "the press happened and the request it should have caused did not".

## 3. Open questions

Each is a question with an owner, not a task with a date.

| Question | Why it is open | Who would answer it |
|---|---|---|
| Should a core restart restore the last recorded generation? | The history store makes the data available and nothing uses it automatically. Restoring would turn a crash into a pause; not restoring keeps a restart predictable, and a restart that silently rewinds the clock is its own surprise | the version that takes up VWR-07 |
| Is the 1 MiB request-body cap the right ceiling? | Setting 100,000 cells needed three requests in the measurement in [testing.md](testing.md) §5.3, because one body would have exceeded the cap. A larger cap trades a larger memory window for fewer round trips, and the right answer depends on how bulk editing is expected to work | the version that takes up bulk editing |
| Should the API bound a `cells` payload, or only the `bits` allocation? | VWR-05 records that it currently bounds only the allocation. A payload cap would be a second rule, and the page already bounds itself | the version that takes up VWR-05 |
| Should a representation switch be refused while one is running, or queued? | It is refused today, so a person who clicks the control twice sees the second click fail. | Should the page hold its stream open while the tab is hidden? | A hidden tab keeps a connection and keeps receiving frames the person cannot see.
