# v0.3.0 — a localised interface, one source per value, and a history timeline

## Scope

Version `v0.3.0` owns phase 03 milestone 00
([../docs/plan/phase-03-service-and-ui/milestones.md](../docs/plan/phase-03-service-and-ui/milestones.md)):
a Chinese and English interface, a single declaration point for every shared
value, one style rule per kind of control, and the recorded history shown as a
timeline the page can roll back from. Version state is owned by
[../docs/plan/VERSIONS.md](../docs/plan/VERSIONS.md); the focused plan is
[../docs/plan/phase-03-service-and-ui/plans/v0.3.0/plan.md](../docs/plan/phase-03-service-and-ui/plans/v0.3.0/plan.md).

This is the first version of phase 03. Phases 01 and 02 built an environment, a
world, two storages and a history; this one is about the surface a person
actually touches, and it began with an audit rather than a feature.

## Environment

Profile `M1`, unchanged: CPython 3.14.7 (uv 0.12.15) with numpy 2.5.3, Node.js
v24.19.0, GCC 16.1.0 and CMake 4.4.2 for the C++ gate, PowerShell 5.1. No new
dependency: the history database is SQLite from the standard library, and the
interface is ES modules with no build step.

## The audit that started the version

The request was specific: things that can be shared should be shared, and
nothing should be written twice — naming, as an example, a style that the
sparse/tiled control ignored. The audit found five classes of duplication and
two style rules that did not apply where they appeared to.

| Value or rule | Copies found | Where |
|---|---|---|
| `MAX_FRAME_CELLS` and the frame admission rule | 2 | `frame-rules.mjs`, `public/viewport.mjs` |
| maximum ticks per second | 4 | `events.mjs`, `app.js`, `index.html` twice, and the core's own `bridge.py` |
| default world size | 10 | `bridge.mjs` twice, `events.mjs`, `frame-rules.mjs`, `server.mjs` four times, `app.js`, and the core |
| default subscription rectangle | 4 | `events.mjs`, `frame-rules.mjs`, `viewport.mjs` twice |
| grid line threshold | 2 | `app.js`, `viewport.mjs` |
| the control-group layout rule | 1, applied to 2 of 3 groups | `style.css`: `.tps, .grid-width` omits `.representation` |
| the select appearance rule | 1, scoped to one control | `style.css`: `.grid-width select`, so the sparse/tiled select had no styling at all |

The last two are what the request pointed at, and they are the same defect in two
forms: a rule written for the controls that existed when it was written, and
applied to the controls that exist now only if someone remembers. The fix is not
to add `.representation` to the selector; it is to stop writing a selector that
enumerates controls.

### The three claims of the version

**One catalogue.** `public/locales.mjs` holds two key sets, English and Chinese,
and the markup carries structure only — no visible text. A test compares the two
key sets for equality and rejects an empty value, so a missing translation fails
a gate instead of reaching a user. The core's own `message` fields are
diagnostics and are passed through untranslated; the protocol's error *codes*
have localised labels, because a code is part of the contract and a message is
not.

**One source per value.** The frame budget and its admission rule collapsed into
`public/shared.mjs`, which both the service and the page import — the page's own
directory, because the service can read it and the browser can too, which is what
makes "the browser cannot import a server module" stop being a reason to keep two
copies. The limits the *core* enforces are now advertised in the handshake and
consumed from there: the tick-rate bounds, the step limit, the coordinate limit
and the storage choices. A page that offers a rate the core refuses is a page
that lies, and the copy that drifts is always the client's.

**One style rule per kind.** Every control group shares one layout rule and every
select one appearance rule, and a test audits the stylesheet for a rule that no
element can match or that applies to one control and not its siblings. The audit
is the part that matters: the defect was not a missing rule but a rule that
enumerated its subjects.

## Failures

### F24 — an edit between two generations made the recorded chain unreplayable

The core gained the ability to record its own history this version. The first
end-to-end attempt was: set a glider, step four generations, roll back to
generation one. It answered:

```
generation 1 kills (1, 0), which is not alive; the recorded chain is not a life history
```

The store's replay validation had caught a real inconsistency, and it was right
to. Generation zero had been recorded at start-up, when the world was empty. The
`set` that followed changed the world without recording anything, so generation
zero described a world that no longer existed and the delta into generation one
described a transition from a state that never happened.

The fix is a contract, not a patch: **any operation that changes the world
between two recorded generations must re-keyframe the generation it happened
at.** A mutation now records the current generation as a keyframe, which replaces
the row rather than appending, so generation zero describes the world *after* the
edit and the chain replays.

Two things are worth recording about how this was found. It was found by the
validation that already existed, not by a test, which is the first time this
project's defensive check has caught a defect in new code rather than in the code
it was written for. And the error message could say what was wrong but not why:
the cause was three layers up, in the protocol, while the report came from the
store.

### F25 — the service did not stop its core, so a restart left an orphan

The viewer's history test began failing with
`EBUSY: resource busy or locked` when it tried to remove the SQLite store. The
first read was a test problem — a file still open on Windows — and the first fix
was to retry and to delete the `-wal` and `-shm` sidecars that the original
cleanup had missed, which is a real defect in its own right.

It did not help, and the reason was worse than the symptom. Counting processes
after a whole-file run showed **two Node processes and two Python processes still
alive**. The teardown ordering meant the test's cleanup ran before the viewer's
own shutdown, so the core was still running; but a core that is merely still
running during teardown is not a leak. The leak is that a core started with
`--history` **holds the store open and keeps writing to it**, so an orphan is not
an idle process — it is a second writer on a database another process is using.

The fix is in the test's teardown, which now stops the core explicitly instead of
depending on which hook the runner happens to schedule first, and waits with a
retry for the operating system to release the file. A single test in isolation
had always passed, which is why it took a whole-file run and a process count to
see it.

This is recorded as a risk with an owner rather than closed: the *server* stops
its bridge correctly (`closeViewer` awaits `bridge.stop()`), and the leak came
from a teardown that ran around it. A future service that crashes, or is killed,
can still leave a core holding the store, and nothing yet detects a second writer
on one history database.

### F26 — the style rules that the request pointed at

Two style rules were found to be in the defect class the request named, and both
are recorded rather than quietly fixed:

* `.tps, .grid-width` is a layout rule that enumerates its subjects, so the
  control added by the previous version was not in it and did not get the shared
  layout.
* `.grid-width select` scopes an appearance rule to one control, so the
  sparse/tiled select rendered with the browser's default styling: a different
  height, no border from the palette, and no relationship to the control next to
  it.

Neither is a functional bug and both are exactly what the request was about. The
version's answer is a test that audits the stylesheet for unreachable rules and
for rules scoped to a single control, so the next control added inherits the
shared rules and a rule that does not apply fails rather than being invisible.

## Deviations from the plan

| Planned | Delivered | Reason |
|---|---|---|
| The history is a feature of the core, not of the service | The core records when `--history` is given, and the service passes it by default | The store is Python and the world is Python; making the Node service own the history would have meant a second process. The boundary is kept by injection: the world module does not import the store, and only the console entry point knows both. |
| Localisation covers the interface | Localisation covers the interface and **not** the core's diagnostics | A translated diagnostic is harder to search for and is read by whoever is fixing a fault. The protocol's codes are the contract and are labelled; the messages are data and are passed through. |
| The timeline shows the recorded generations | The timeline shows them, and a representation switch starts a new one | A new core process is a new session, so the timeline restarts at the generation carried over. Recorded as a risk owned by the next version rather than hidden. |
