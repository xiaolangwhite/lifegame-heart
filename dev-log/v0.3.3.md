# v0.3.3 — the history page as a workspace, and the view a page opens with

## Scope

Version `v0.3.3` owns phase 03 milestone 03
([../docs/plan/phase-03-service-and-ui/milestones.md](../docs/plan/phase-03-service-and-ui/milestones.md)):
the main view opens at a span derived from the canvas and centred on the world,
and the history route becomes a compact, draggable, selectable tree on the left
with a preview of the selected generation on the right. Version state is owned by
[../docs/plan/VERSIONS.md](../docs/plan/VERSIONS.md).

## The two requests

The request that created this milestone named two things.

1. *"When the main view shows, its default span is the horizontal screen pixel
   count over 60, and the viewpoint is at the world's centre."* The old default
   was a fixed `DEFAULT_SPAN = 1024`, so what a person saw first depended on a
   number nobody could see, and a view narrower than the world showed a corner of
   it.
2. *"The history page cannot show a tree; rows stack and overlap, and a single row
   fills the screen, which wastes space and says very little."* That is a report
   about a defect a person could see, and the first job was to find out why.

## The defect, diagnosed before anything was changed

Three causes, all in the drawn row rather than in the arithmetic:

| Symptom | Cause |
|---|---|
| A single row filled the width | The row was `inline-size: 100%` of a page-wide column. There was no second pane, so one generation occupied the whole stage with one number in it. |
| Rows stacked and "overlapped" | `.timeline-row` was a grid with four explicit tracks, and the branch, fork, head and current marks were *appended* to it as extra items. With no `grid-auto-flow`, the fifth and later items fell into implicit **rows**: one node became two or three lines tall, and the marks appeared to stack on top of each other. |
| The row grew when it was looked at | The node's numbers were grid items in the flow and were revealed by animating `max-inline-size` from `0` to `26ch`. Opening them re-sized the tracks, and on a row that had already overflowed into implicit rows it added another line, so the rows below moved. |
| No tree was visible | Indentation was `padding-inline: calc(4px + var(--depth) * 14px)` and nothing else. A nest that only moves sideways by 14 px, in a row whose own content starts at the same place, reads as a list with an uneven left edge. A window that cut a branch root also rebased the depth, so the offset could vanish entirely. |

The last one was the design's own fault: the row had no connector, so the tree
relation lived only in a padding value.

## What was built

**The default view is a function of the canvas, and there is exactly one
declaration of it.** `public/viewport.mjs` owns `DEFAULT_PIXELS_PER_CELL` (60),
`defaultSpan(cssWidth)`, `worldCentre(world)` and `centreViewport(...)`; the world
route and the preview canvas both call them, so a cell is the same size in both.
`DEFAULT_SPAN`, `DEFAULT_ASPECT` and `DEFAULT_SUBSCRIPTION` are gone.

There is **no service-side default any more**. The push hub used to hand a client
that had not named a rectangle the fixed `DEFAULT_SUBSCRIPTION`, which for the
design-target world is a whole-world frame pushed to a page that is about to say
where it is really looking. A client without a rectangle now receives `hello` and
nothing else until it subscribes; the page publishes immediately after `hello`.

The origin puts the **world's** centre in the middle of the view:
`x0 = round(width / 2 - span / 2)`, and `y0 = round(height / 2 - visibleHeight / 2)`.
The second is the general form of the `span / 2` the request states, which is
exactly right on a square canvas and off-centre on every other one; the anchor is
asserted for four canvas aspects.

Neither half is decided before it is known: the span needs a canvas the layout has
given a size to (a canvas the full-width panel state has hidden measures zero) and
the origin needs the world from `hello`. Until both are there the route asks for
no frame at all. A resize re-derives the span **only while the view is still the
page's**; after the first pan, zoom or pinch it belongs to the user.

The route also remembers where it is looking, in world coordinates, under
`lifegame.viewer.focus` (`public/focus.mjs`).

**The history route is two panes.** The tree is a column on the left that scrolls
on its own; the preview is a canvas on the right with its own viewport, its own
pan and zoom, and the same default span rule as the world canvas.

**A row is one line tall, whatever it is showing.** The generation and one
container of marks are the row's only in-flow children, so the two of them always
fit the two tracks; the node's numbers live in `.timeline-overlay`, which is
`position: absolute` and therefore cannot change the row's height; the connector
gutter is absolute for the same reason. The reveal is one state the page sets —
`data-open` — for the pointer and the keyboard alike, which replaced
`:hover`/`:focus-visible` (two rules the stylesheet had to keep in step and
neither of which any test could reach).

**Indentation is fork depth, and every level carries a connector.** Each flattened
node now carries a `guides` array — `line` for a branch with a later sibling,
`elbow` where a branch starts and something follows, `end` where it starts and
nothing does, `blank` for a chain below the last branch — and the page renders one
14 px cell per level inside the row's own indentation, so a connector is drawn
exactly above its parent's. Two children of one fork differ by glyph and by
branch letter, not only by offset.

**The tree is draggable.** Pointer Events on the list pan it (`scrollTop`/
`scrollLeft`), with `touch-action: none` so a touch drag cannot be stolen by the
page scroll, and the same four-pixel threshold the world canvas uses: a drag that
travelled is not a click, so panning never moves the working point. `↑`/`↓`/
`Home`/`End` move along the tree, because forty rows is forty tab stops otherwise.

**The preview looks where the person was working.** A click sends `select` (which
moves the world and the working point), then the page reads the live set **once**
through the new `GET /api/cells`, finds the cell nearest to the remembered focus
point, centres the preview on it, and frames it once. Nothing is scanned per
frame. `GET /api/cells` is the core's own `export` wrapped for that one purpose,
and past `MAX_CELLS_FOR_NEAREST` (16384 cells: 128 KiB of payload, about 171 KiB
of base64, declared in `public/shared.mjs`) it returns the population and the
core's `bounds` instead, which the page states in words beside the canvas.

**Two canvases now paint the same world with one implementation.**
`public/frame-draw.mjs` holds `drawFrame`, `paintBits`, `drawGrid`,
`readPalette` and `DEFAULT_PALETTE`; the world page and the preview call it. The
palette and the render paths used to live in `pages/world.js`, and a second copy
in the preview would have been the copy that drifts.

New tests this version adds, beyond the ones it updates: that the first view is the

a live set above the cap degrades to the bounds and says so; that dragging the tree
pans it without selecting; that the arrows move along the tree; and that the
preview pans and zooms without touching the selection.

## Failures

### F33 — the row's own layout was the defect, and the mark items were the reason

The reported "duplicated stacking" was not a CSS specificity problem or a browser
difference: four explicit grid tracks plus four appended marks meant `ceil(8 / 4)`
lines on a node that had every mark. The first fix attempted was a fifth track and
`grid-auto-flow: column`; what actually settled it was moving the marks into one
container and the numbers out of the flow, so the number of items can no longer
depend on the row's state. The lesson recorded: when a row's height depends on
*how many* children it has, the row's layout will encode the data's shape, and
data shapes change.

### F34 — a stub that was only accidentally right

`tests/page.test.mjs`'s core stub encoded a `bits` frame from the *absolute*
coordinates of the live cells. The real core encodes a bitmap **of the
rectangle** (`world.viewport(x0, y0, w, h)`), so the stub was right only while
every frame started at the origin — which every test did, because the old default
view was the whole world. Deriving the default view from the canvas moved the
origin to (25, 27) and the stub painted nothing, which is how the divergence
surfaced. The stub now translates, and a test's dense-block coordinates are chosen
from the frame the page actually asks for.

### F35 — `state` does not exist at module scope

The history module created its `ResizeObserver` in its own module body, where the
shell's shared state has not arrived yet (the handshake fills it after the module
runs). `state.resizeObserver = …` threw, the page module never started, and every
history case failed with a null dereference while the world route stayed green.
The observer is created in `start()` now, which is the same place the world route
does its own setup.

### F36 — panning a preview that never asked for a frame

The preview's drag updated its viewport and did not fetch a frame, so a pan was
visible only after something else triggered a fetch. It now re-frames on every
move, coalesced to one request in flight with the same flag pair the world route
uses.

### F37 — a documentation gate failure that arrived with the task

The first `verify.ps1 -Full` run of this version reported `documentation
conformance` failed with `docs/plan/VERSIONS.md:24 markdown link target does not
exist: ../../dev-log/v0.3.3.md` — the version row for *this* work was already in
the tree and linked to a dev-log entry that did not exist yet. This entry is that
file; with it the gate is eleven of eleven. It is recorded here because the failure
looked like a code change and was not.

## Deviations from the plan

| Planned | Delivered | Reason |
|---|---|---|
| The request's origin formula for both axes | The general centring formula, which reduces to it on a square canvas | The stated `y0 = round(height / 2 - span / 2)` puts the world's centre *above* the middle on any canvas that is not square, because the visible height is `span * cssHeight / cssWidth`. The requirement it explains ("the viewpoint is at the world's centre") and the assertion for it both hold with the general form, and a test pins the square case to the stated formula. |
| The default span as "60 cells across" | One cell per 60 CSS pixels of canvas width | The formula given (`horizontal pixel count / 60`) and the parenthetical ("60 cells across") cannot both hold; the formula and the explicit assertion (`span == width / 60`) agree with each other, so they were followed and the parenthetical is recorded here as the reading that was not taken. **Confirmed by the person who asked for it**, after the conflict was put to them: the formula is the intent, and the parenthetical was the relaying agent's error rather than theirs. Nothing changed in the code as a result — what changed is that this is now a decision on the record instead of a choice made on their behalf. |
| `GET /api/cells` as a possible route | Delivered as described | — |
| The history page's detail overlay as `:hover`/`:focus-visible` | One `data-open` state the page sets for both the pointer and the keyboard | Two mechanisms for one reveal is two things to keep in step, and neither could be exercised without a browser while the row's geometry is the thing under test. |
