# v0.2.0 — sparse world, rule evaluation and an interactive viewer

## Scope

Version `v0.2.0` owns phase 02 milestone 00
([../docs/plan/phase-02-simulation-core/milestones.md](../docs/plan/phase-02-simulation-core/milestones.md)):
a world that fits the design target of 65536 x 65536, Conway's rule evaluated
against an independent oracle, a line protocol another process can drive, and a
browser page that edits and runs the world. Version state is owned by
[../docs/plan/VERSIONS.md](../docs/plan/VERSIONS.md); the focused plan is
[../docs/plan/phase-02-simulation-core/plans/v0.2.0/plan.md](../docs/plan/phase-02-simulation-core/plans/v0.2.0/plan.md).

## Environment

Profile `M1`, declared in
[../docs/plan/PERFORMANCE_ACCEPTANCE.md](../docs/plan/PERFORMANCE_ACCEPTANCE.md) §1.1.
CPython 3.14.7 (uv 0.12.15) with **numpy 2.5.3**, Node.js v24.19.0 with pnpm
12.6.0, GCC 16.1.0 and CMake 4.4.2 for the C++ gate, PowerShell 5.1.

numpy is a new runtime dependency for this version; the wheel for CPython 3.14
on Windows x86-64 was verified available before the decision was taken, and the
decision with its native boundary, build integration and portable fallback is
[ADR 0006](../docs/adr/simulation-core/0006-numpy-is-the-vectorised-substrate.md).
The project switched from a virtual uv project to a packaged one
(`uv_build`, `src/` layout) in the same change, because there is now an
importable library.

### The measured frontier

Profile `M1`, 1024 x 1024 world, a still life of blocks so the population does
not drift, one warm-up step then five timed generations, `min` and `median`
recorded:

| Live cells | Sparse, ms per generation | Dense reference, ms per generation | Naive pure Python, ms per generation |
|---|---|---|---|
| 400 | 0.181 | 13.643 | 0.709 |
| 4,000 | 1.359 | 13.931 | 8.468 |
| 40,000 | 15.361 | 14.313 | not measured above 20,000 |
| 200,000 | 106.493 | 14.327 | |
| 260,000 | 138.171 | 13.224 | |

A second run of the same ladder measured 12.879 ms at 40,000 and 101.020 ms at
260,000, with the 400-cell row identical. Both are recorded; only what they
share is used, and the per-cell constant is stated as a range.

The dense reference is flat in the population and the sparse step is linear in
it, so the crossover is at about **40,000 live cells** — four percent of that
world, three times earlier than the one-in-nine density the algorithm's shape
suggests. At the design target, one percent density is 43 million live cells,
which the measured constants put at 17 to 23 seconds per generation.

**That is an unresolved gap, not a result.** It is recorded in
[ADR 0009](../docs/adr/simulation-core/0009-sort-based-sparse-does-not-scale-to-the-target.md),
carried as phase risk R10, and owned by the version that names phase 02
milestone 01. What this version can claim is that the target-scale world
*exists*: it can be constructed, edited and stepped, and its memory is
proportional to its population.

## Failures

### F13 — the neighbour count subtracted the self-entry from dead cells too

The first sparse step computed `neighbours = occurrences - 1` for every
candidate. That is right for a live candidate, which appears once on its own
account plus once per live neighbour, and wrong for a dead one, which appears
only once per live neighbour. Every birth was therefore undercounted by one.

How it surfaced: a hand-computed glider. Generation one of a glider has five
cells; the code produced three. Bounds went to `(1,1,2,2)` instead of
`(0,1,2,3)`.

Fixed by subtracting the self-entry only where the candidate is alive:
`neighbours = occurrences - was_alive`.

The random-state equivalence test in
`tests/world/test_oracle_equivalence.py` catches this class of defect
immediately, and its module docstring now records the story. The pattern list
alone would have needed the glider to be in it to notice.

### F14 — the frame encoding compared a bit count against a byte count

`encode_frame` chooses between two encodings by size. Its rule was written as
`cell_bytes * 8 <= bitmap_bytes`, where `cell_bytes` is already a byte count and
`bitmap_bytes` is also a byte count. The extra factor of eight made the
crossover one live cell per 512 cells instead of the one per 64 the function's
own docstring states.

Consequence: bandwidth only, never correctness — a coordinate list up to eight
times larger than the bitmap it was chosen over, in the band between one in 512
and one in 64.

How it surfaced: review of the module while writing its contract, not by a
failing test. The two existing tests that exercise the encodings sit on
rectangles where both rules agree. Fixed by comparing bytes with bytes, and a
new test now pins the boundary exactly: a 64 x 64 rectangle has a 512-byte
bitmap, so 64 live cells are sent as coordinates and 65 as the bitmap.

The same review found that the viewer's frame admission rule had been derived
from the encoder with the same fourfold-and-then-some error and documented as
"the encoder's own rule". It is corrected to `population * 64 <= area` in
`src/viewer/server.mjs` and `src/viewer/public/app.js`, its boundary case in
`server.test.mjs` now uses a population that genuinely forces the bitmap, and
`src/viewer/README.md` states the rule it actually implements. The guarantee is
made against the last reported population, so a world that grows between the
state poll and the request can still take the bitmap path; the area cap bounds
that allocation at `MAX_FRAME_CELLS` bytes.

Two follow-through items from that correction, both found by reviewing it
afterwards:

* The module docstrings in `server.mjs` and `public/app.js` still stated the
  superseded rule while the code below them used the corrected one. The
  constants were right and the prose was wrong, which is the harder direction to
  notice. Both now state the rule the code implements.
* Nothing pinned the corrected rule. Every admission case in the test file sat
  outside the band where the two rules disagree, so reverting the constant would
  have left the suite green. A case now sits inside that band by construction —
  4097 x 4097 with 100,000 live cells, where the encoder chooses `cells` and the
  wider rule would have refused — and it asserts both the admission and that the
  request reached the core.

### F15 — a single timing reading was wrong, and the second measurement said so

While profiling the sparse step, one reading put `numpy.unique` at 444 ms on
data the whole step was measured at 127 ms to process — self-contradictory. The
machine was under load from concurrent work. Re-measured with the two counting
paths interleaved on the same data in one process, `unique` costs about 49 ms
and `numpy.sort` about 37 ms.

Nothing was changed on the strength of the bad reading. The lesson is recorded
in the module's `performance.md`: a single cell of a measurement matrix is not a
measurement until it has been reproduced under the same conditions.

|---|---|---|
| Phase 02 delivers the core; the service and UI are phase 03 | A minimal NodeJS service and a browser page are delivered here | The world was asked to be observable and editable in this milestone, and a Python process serving a line protocol has no way to be clicked. The alternative — a Python-side viewer — would have introduced a UI outside the documented split for a surface phase 03 replaces anyway. Recorded as [ADR 0007](../docs/adr/service-and-api/0007-viewer-service-delivered-in-phase-02.md). |
| The world and its rule only | The world, the rule, a dense oracle, a line protocol and a viewer | The oracle is not decoration: it is what found F13, and it is the measured baseline the sparse world has to beat. |
| `node --test src/viewer/tests/` as the viewer command | `node --test "src/viewer/tests/*.test.mjs"` | Node 24 does not accept the directory form; it tries to load the directory as a module. |
