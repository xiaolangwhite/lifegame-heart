# v0.3.6fix1 — a damaged store can be salvaged

## Scope

The fix for `STO-19`, the one defect the store register reported as unowned: a
schema-2 store whose own rows already violated the declared keys could not be
opened at all, and its owner had no path forward this module offered. The refusal
stays; what is new is a way to repair a **copy**. Version state is owned by
[../docs/plan/VERSIONS.md](../docs/plan/VERSIONS.md).

## Results

The default answer is unchanged: opening a damaged store in place migrates or
refuses, and a rebuild that would hold a dangling reference rolls the whole
transaction back and leaves the file as it was. That is the right answer for a
file opened where it lies.

`salvage(source, target)` is the path forward. It copies the source with SQLite's
`VACUUM INTO`, which reads a consistent snapshot and opens the source read-only,
so the damaged file is never written to. It then opens the **copy** with
`repair_dangling=True`: during the migration, a row whose `parent_id` names no row
gets that link cleared, and its id is recorded in `Store.repaired_dangling`. The
foreign-key check then passes and the copy is committed as the current schema.

What a cleared link means is stated rather than smoothed over. The row starts a
branch with no parent. If its payload is a delta — which is what a middle node
usually is — that branch has no keyframe and `state_at_node` refuses it with
`no keyframe on its path to the root`, while the intact part of the store stays
readable. The damage is bounded and named instead of the whole file being
unopenable.

The CLI exposes it as `python -m lifegame.store salvage SOURCE TARGET`; the target
is refused if it already exists, and the command prints the session count and the
cleared row ids.

## Failures

None. The migration repair is exercised by two cases: one that salvages a copy,
asserts the cleared row, the readable intact chain and the refusal on the damaged
branch, and asserts the source is byte-identical and still refused; and one that
asserts an existing target is not overwritten.

## Deviations from the plan

| Planned | Delivered | Reason |
|---|---|---|
| Give a damaged store a path forward | The path is a copy, not an in-place repair | The damaged file may be a person's only copy; the refusal is kept and the repair never writes to the source |
| Repair the dangling link | Clear it, report the row, and leave the branch refusing a replay | The keyframe that would explain the row was on the lost path; inventing a state would be worse than a named refusal |
| Cover both dialects | SQLite only | The dangling-link case is a schema-2 SQLite store, and copy-then-migrate is defined in terms of a file. The MySQL side of the store is already the unverified path STO-01 records |
