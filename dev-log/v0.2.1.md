# v0.2.1 — the tiled representation and two viewer interfaces

## Scope

Version `v0.2.1` owns phase 02 milestone 01
([../docs/plan/phase-02-simulation-core/milestones.md](../docs/plan/phase-02-simulation-core/milestones.md)):
the tiled bit-parallel representation that
[ADR 0009](../docs/adr/simulation-core/0009-sort-based-sparse-does-not-scale-to-the-target.md)

[../docs/plan/phase-02-simulation-core/plans/v0.2.1/plan.md](../docs/plan/phase-02-simulation-core/plans/v0.2.1/plan.md).

## Environment

Profile `M1`, unchanged from the previous version: CPython 3.14.7 (uv 0.12.15)
with numpy 2.5.3, Node.js v24.19.0 with pnpm, GCC 16.1.0 and CMake 4.4.2 for the
C++ gate, PowerShell 5.1. No new dependency was added; the tiled world is built
from `numpy.uint64` arrays and `numpy.unpackbits`.

## What was built

The world is cut into 64 x 64 tiles, each tile 64 machine words of 64 cells, and
only non-empty tiles are stored. A step advances every active tile at once with
a bit-parallel adder tree: eight neighbour bit-planes, a ripple-carry four-bit
counter, and

```
next = ~s3 & ~s2 & s1 & (alive | s0)
```

which is the standard formulation of "born on three, survives on two or three"
over the count bits.

The active set is every non-empty tile **plus the neighbours of any tile whose
border is not empty**, because a birth can only appear in a tile adjacent to a
live cell. In a dense region those neighbours already exist and the expansion is
free; it costs up to nine times for isolated tiles, which is exactly the shape
the sparse world is better at.

The step is vectorised across tiles **and** rows: an active set of `M` tiles is
an `(M, 64)` array, so the whole adder tree is a few dozen array operations
rather than a Python loop over tiles. A per-tile loop would have drowned in
interpreter overhead, and that is the reason this shape of the algorithm works
in numpy at all.

### The two viewer interfaces

**A thicker, adjustable grid.** The line width was hard-coded at one CSS pixel;
it is now a choice of one to four, defaulting to two, and it is snapped to whole
**device** pixels rather than CSS pixels. At a device pixel ratio of 1.25 the
"2 px" setting becomes 2.4 CSS pixels, which is the nearest width that actually
renders as two clean lines instead of blurring across three. Grid lines are
still only drawn when a cell is at least six pixels across, and the grid colour
moved into a CSS variable so it can be seen in a light theme at all.

**A dark and light theme, including the canvas.** The theme is a concrete value
on the document element rather than a media query, set by an inline script
before the first paint, so the stylesheet needs two blocks and the rule "follow
the system unless the user chose otherwise" lives in exactly one module. Cell
and grid colours are read back from the stylesheet through `getComputedStyle`
and cached; switching themes refreshes the cache and repaints the frame already
held, without a network request. A colour that cannot be parsed leaves the
previous colour in place rather than painting black.

Contrast was computed from the stylesheet with the WCAG formula rather than
judged by eye: the live cell is 11.83:1 against the background in the dark theme
and 6.01:1 in the light one, both far above the 3:1 a non-text graphic needs.

The inline script cannot import a module, and a deferred module runs after the
first paint, so the storage key and the precedence rule are duplicated in five
lines of the page. That duplication is deliberate, is commented as such, and is
**pinned by a test** that fails if the inline script and the module disagree
about the key.

### The frontier, on two shapes of population

Profile `M1`, 1024 x 1024, still lifes of 2 x 2 blocks so the population cannot
drift, one warm-up step then five timed generations. The harness asserts the
population is unchanged, so a measurement taken on a drifting pattern fails
rather than being reported.

**Clustered** — the blocks packed together:

| Live cells | Sparse | Dense reference | Tiled | Tiles |
|---|---|---|---|---|
| 400 | 0.175 ms | 12.930 ms | 0.303 ms | 1 |
| 4,000 | 1.371 ms | 13.125 ms | **0.330 ms** | 4 |
| 40,000 | 13.931 ms | 13.397 ms | **0.537 ms** | 49 |
| 200,000 | 84.061 ms | 14.224 ms | **1.955 ms** | 196 |
| 260,000 | 119.341 ms | 13.565 ms | **2.175 ms** | 256 |

**Scattered** — the same blocks spread one per tile:

| Live cells | Sparse | Dense reference | Tiled | Tiles |
|---|---|---|---|---|
| 400 | **0.175 ms** | 13.430 ms | 0.652 ms | 32 |
| 4,000 | **1.402 ms** | 13.234 ms | 2.003 ms | 256 |
| 4,096 | **1.430 ms** | 13.296 ms | 1.984 ms | 256 |

The tiled step costs a constant per active tile; the sparse step costs a
constant per live cell. They cross at about **4,000 live cells when clustered**,
and the sparse world wins throughout when scattered, because every isolated tile
pays for eight neighbours that hold nothing.

Projected to the design target, and labelled a projection because the ladder has
never been run there. **The projection has two halves, and the first draft of
this entry quoted only one of them.** One percent of 65536 x 65536 is 43 million
live cells, and what matters is not how many there are but how they are spread,
because a tiled step costs a constant per active tile:

| One percent, 43 million live cells | Active tiles | Tiled | Sparse |
|---|---|---|---|
| packed together, about 4,096 cells per tile | about 10,500 | **0.08 to 0.09 s per generation** | 17 to 23 s |
| spread evenly, about 41 cells per tile | about 1,048,576 | **7.8 to 8.9 s per generation** | 17 to 23 s |

So the tiled advantage over the sparse step is about two hundred times when the
population is compact and about twice when it is spread. Quoting only the
compact case would have overstated the result by two orders of magnitude, and
the correction came from reviewing the module contract's own projection rather
than from any test.

That closes, for the compact shape, the gap this project recorded one version
ago. It does not close it for a population spread evenly across the target, and
it does not make the target scale measured.

Querying pulls the other way and the record says so. At 260,000 live cells one
`state` request costs 9.41 ms tiled against 1.27 ms sparse, and a 1024 x 1024
frame costs 12.00 ms against 3.75 ms, because the tiled store has to be
unpacked. Stepping and querying favour different representations, which is why
the default was not changed on the strength of the step measurement alone.

## Failures

### F16 — a change count taken over words instead of over bits

The first tiled step reported how many cells changed as
`np.count_nonzero(after != before)`, which is correct for the sparse world where
one array element is one cell, and wrong for the tiled world where one array
element is a **64-cell word**. Four changed cells falling inside three rows were
reported as three.

How it surfaced: not from the oracle test. Every state comparison passed — the
population, the live set, the bounds and every viewport were correct — and the
symptom only appeared in the protocol, where one representation answered
`changed: 4` and the other `changed: 3` for the same glider. Chasing it meant
stepping both representations in lockstep and printing the count per generation:
sparse and dense said four every time, tiled said 3, 2, 3, 4, 3, 2.

Fixed by counting bits rather than elements:
`int(np.bitwise_count(after ^ before).sum())`.

The shared contract now covers the value `step` returns, not only the state it
produces, and the assertion that caught it stays as
`assert_same_change_count` in `tests/world/test_oracle_equivalence.py`. The
general lesson is recorded because it will recur: agreement between two
implementations on their *state* is not agreement on their *interface*.

### F17 — two test patterns designed to fail in the wrong way

Two of the new tiled tests failed on first run, and both were the test's fault
rather than the code's:

* a horizontal three-cell line was placed to produce a birth in the next tile,
  which it does not — the pattern is a blinker that oscillates in place. Three
  cells in a **vertical** line produce the intended birth, and the test was
  rewritten around one;
* a check for cells beyond the edge of a partial tile called `is_alive` with an
  out-of-range coordinate, which correctly raises. The check now runs over the
  live set, which is what "must never appear" actually means.

Neither is interesting on its own. They are recorded because "the test failed"
and "the code failed" are different findings, and the first instinct on a red
suite is to assume the second.

### F18 — the dense render path referenced a constant that no longer existed

Moving the canvas colours into the stylesheet deleted the module constants
`ALIVE_RGB`, `DEAD_CSS` and `GRID_CSS`. One call site was missed: `paintBits`,
the renderer for the dense `bits` encoding, still read `ALIVE_RGB`. Any frame
that arrived as a bitmap would have thrown a reference error and drawn nothing.

`node --check` does not catch this. It parses syntax and does not resolve
bindings, so a file that calls a name which does not exist passes the check that
was being used as the render-path's only automated guard.

How it surfaced: a closing sweep for identifiers that no longer exist, not a
test. Three things were changed rather than one:

* the call site now reads the cached palette, like the coordinate path;
* the assertion was strengthened from "the file does not *declare* the old
  constant" to "the identifier does not appear in the file at all";
* two contract tests were added for the class of defect — every name a module
  imports must exist, and every field read off the palette must be declared.

Both new assertions were shown to bite by mutating the sources: replacing the
light theme's live colour with a notation the parser cannot read, and renaming
`aliveRgb` to `aliveRGB`. Each mutation produced its own specific failure and a
non-zero exit, and each was reverted before the suite was re-run green.

### F19 — a correction to this version's own headline projection

The first draft of this entry, of [ADR 0010](../docs/adr/simulation-core/0010-tiled-bit-parallel-representation.md)
and of [PERFORMANCE_ACCEPTANCE.md](../docs/plan/PERFORMANCE_ACCEPTANCE.md) §5.2
projected one percent density at the design target as "about 10,500 tiles,
about 89 milliseconds per generation". That is true only if the 43 million live
cells are packed almost solidly into their tiles.

A tiled step costs a constant per **active tile**, so the same one percent
spread evenly across the world — about 41 cells per tile — fills essentially all
1,048,576 tiles and projects to **7.8 to 8.9 seconds per generation** instead.
The sparse step needs 17 to 23 seconds for that population, so the advantage
falls from about two hundred times to about twice.

The error was not arithmetic, it was a missing case: one number was quoted for a
quantity that depends on how the population is distributed. The tiled advantage
comes from spatial compactness, not from the size of the population, and all
three documents now state both halves side by side. It was found by reviewing
the module contract's own projection against the code, not by a test, and it is
recorded here because the corrected claim is much weaker than the one it
replaced and that is the point.
