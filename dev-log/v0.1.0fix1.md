# v0.1.0fix1 — verification cost, determinism and entry points

## Scope

A `fix` on the completed three-component parent
[../docs/plan/VERSIONS.md](../docs/plan/VERSIONS.md) `v0.1.0`
([../docs/plan/phase-01-foundation/milestones.md](../docs/plan/phase-01-foundation/milestones.md) M00).
Triggered by a direct report that verification took too long and was too
complex. No acceptance criterion of `v0.1.0` was weakened: the check set grew by
no check and lost none, and the two gates that were broken were repaired rather
than relaxed.

Nothing here changes what is verified. It changes how much of the verification
cost is spent on the claim and how much on the harness around it.

## Environment

Profile `M1`, declared in
[../docs/plan/PERFORMANCE_ACCEPTANCE.md](../docs/plan/PERFORMANCE_ACCEPTANCE.md) §1.1.
Same toolchain as `v0.1.0`: CPython 3.14.7 (uv 0.12.15), Node.js v24.19.0 /
pnpm 12.6.0, GCC 16.1.0 and CMake 4.4.2 for the C++ gate, PowerShell 5.1.

## Diagnosis

Each component was measured three times or more before anything was changed.
Two of the three findings were defects, not tuning opportunities.

### D1 — the gate's own test suite spent 98% of its time in process plumbing

`tools/documentation/tests/run-tests.ps1` launched the validator 27 times
through `Start-Process` with redirected standard output and error.

| Measurement | Result |
|---|---|
| One validator run, direct invocation | **63 ms** |
| One validator run, `Start-Process` with redirection | **1033 ms** |
| 27 direct invocations of the same fixtures | **694 ms** |
| The suite as it stood | **28.3 s** |

The validator's own work was 0.7 s of a 28.3 s suite. The rest was process
objects, redirected handles and scratch files that no assertion read — a factor
of sixteen per launch, and about 56% of the whole verification budget.

### D2 — the C++ tool build never checked whether anything had changed

`tools/documentation/build.ps1` called `cmake --build` unconditionally.

| Measurement | Result |
|---|---|
| `cmake --build` with nothing to do | **4.26 s** |
| `build.ps1 -Quiet` with nothing to do | **4.4 s** |
| `build.ps1` after touching one source file | 4.7 s |

The build driver re-checks its cache and regenerates before deciding there is
nothing to do, so "idempotent" cost the price of a real build every time — and
the isolation check calls this script from inside its workload.

### D3 — the isolation check was non-deterministic, and had begun to fail

`scripts/verify-temp-isolation.ps1` required its one exclusion to be re-earned
on every run: either at least five instances of a machine-level temporary
artifact older than the repository, or an observation of that artifact during a
ten-second idle window.

The observed failure, on a tree that had not changed between runs:

```
  history control: 0 instance(s) of the class predate the repository (2026-10-08 12:32:16Z)
  idle control: nothing predates the repository; observing an idle window (10 s)
  idle control: nothing appeared while idle
  exclusion NOT earned: every file created during the workload will count as a violation
dynamic phase: scanned 78680 file(s); 1 changed since the workload started, 0 excused, 1 unexplained
total: 22 checks, 1 failures
exit=1 elapsed=25s
```

A routine operating-system cleanup of the temporary directory had removed the
historical instances, and the idle window happened to be quiet, so a file that
no project tool had written was reported as a violation. The same path slept
for ten seconds and re-scanned 78,000 files, which is why that run took 25 s
where earlier runs of the identical revision had taken 12.7 s.

This is the worst defect of the three: a check that fails for reasons unrelated
to its claim stops being evidence, and it was slow in exactly the case where it
was wrong.

### What was not the problem

* The validator itself: 63 ms for the whole repository.
* The Python and Node gates: pytest 0.7 s, ruff 0.4 s, `pnpm install` 0.09 s.
* The documentation gate: 0.35–0.6 s including PowerShell startup.

## What changed

### `tools/documentation/tests/run-tests.ps1` — direct invocation

`Start-Process` was replaced by a direct call: the exit code comes from
`$LASTEXITCODE` and the report from the output stream, so the suite needs
neither process objects nor scratch files. stderr is dropped inside a locally
relaxed error preference, because the validator writes its summary line there
and a native stderr line would otherwise terminate the run. The determinism
check now hashes the UTF-8 bytes of the decoded stdout text instead of hashing
two files it wrote itself. The retry loop, the scratch output directory and the
`StdoutPath`/`StderrPath` fields are gone. Case coverage and assertion count are
unchanged.

### `tools/documentation/build.ps1` — freshness check

The build is skipped when `build/docguard.exe` is not older than every input
(`src/**` plus `CMakeLists.txt`). `-Clean` still deletes the build directory and
therefore still forces a full rebuild. The reviewer should note the semantic
change: "idempotent build" now means "does not invoke the build system when
nothing changed", and a caller that wants a rebuild must ask for one.

### `scripts/verify-temp-isolation.ps1` — one characterised exclusion

The machine-level artifact class (zero-length, whole name is a GUID, `.tmp`
extension, directly in the system temporary directory) is now characterised
once and evidenced in
[../evidence/windows-temporary-artifact-class.md](../evidence/windows-temporary-artifact-class.md),
instead of being re-derived probabilistically on every run. The excluded shape
is unchanged and remains narrow: any cache entry, build artifact, bytecode file
or package file still fails the check, every excused file is printed, and the
history and idle branches are deleted. The reversal, its reason and the failure
that forced it are recorded in the evidence file, in
[../docs/model/environment/risks.md](../docs/model/environment/risks.md) and in
[../docs/model/environment/testing.md](../docs/model/environment/testing.md).

### `scripts/verify.ps1` — one entry point

Eight gate commands with three invocation conventions and a three-line preamble
that had to be repeated per shell are replaced by one command that sources the
environment itself, runs every gate, and reports a single exit code:

```
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/verify.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/verify.ps1 -Full
```

The default set is feedback for an edit. `-Full` adds the two version-boundary
gates: the isolation dynamic phase and a bootstrap idempotence run. Exit codes:
`0` every gate passed, `1` at least one failed, `2` the runner could not
complete.

The preamble failure mode is not hypothetical: while producing this
measurement, one command in this very session omitted it, the environment
contract silently fell back to the system volume, and the suite went red for a
reason unrelated to any change. The runner removes the opportunity.

## Failures

### F10 — a proof that must be repeated can fail for unrelated reasons

D3 above. The design error is worth naming separately from the symptom. The
exclusion existed to keep a real check honest, and requiring fresh proof of it
on every run looked like the rigorous choice. It was not: the proof depended on
machine state that an unrelated process (a temporary-directory cleanup) could
destroy, and on a stochastic observation window. The check then reported a
violation it could not justify, and took twice as long doing it.

The replacement keeps the honesty by moving the proof to a document that
records the experiment once, with its commands and its negative result, and by
keeping the excluded shape so narrow that a project artifact cannot match it.

### F11 — the harness exclusion pattern matched nothing

Found by review of the isolation script during this fix, and confirmed by
measurement: the pattern that excludes the agent runtime's per-command
temporary directories was

```
\\dsh-[0-9a-zA-Z]{6,}\\
```

which requires six alphanumerics immediately after `dsh-` and then a separator.
The harness actually uses multi-segment names — `dsh-acl-locks`,
`dsh-subprocess-<id>`, `dsh-spill-<id>`, `dsh-workspace-changes-<id>` — so the
pattern broke at the second hyphen.

| Measurement | Result |
|---|---|
| `dsh-*` directories present under the system temporary directory | 46 |
| Matched by the old pattern | **0** |
| Matched by the new pattern `\\dsh-[^\\]*` | **46** |

The consequence had already been observed: one `scripts/verify.ps1 -Full` run
reported `isolation (full, version-boundary) (exit 1)`, and four subsequent
`-Full` runs plus two standalone isolation runs were clean, so the failure could
not be reproduced and the offending path was not captured. The runtime's own
scratch directory is the most likely source; the check now excludes it by the
rule "a path segment that begins with `dsh-`", which is what the header always
claimed it did.

This is the third defect in this version that a warm, passing gate had hidden:
the check reported success because it never looked at the paths it was supposed
to ignore.

### F12 — the entry point did not fix the working directory

`scripts/verify.ps1` sources the environment but left the caller's working
directory alone, so `uv run pytest` with no test path collects nothing when the
caller happens to be in a subdirectory. Measured from `docs/`:
`python tests` exited `5` and the run reported one failed gate out of six. This
is precisely the failure the entry point exists to prevent — a red suite for a
reason unrelated to the change under test.

Resolved by fixing the working directory at the repository root inside the
runner. Verified by running it from `docs/`: six gates, exit 0, and no cache or
temporary directory left behind in `docs/`. The transient locations were never
at risk, because `scripts/env.ps1` exports absolute paths.
