# v0.3.4fix1 — the control that reveals earlier generations

## Scope

Version `v0.3.4fix1` fixes a regression in the interface delivered by the version
`v0.3.4` names, reported by a person using it in a browser. Version state is owned
by [../docs/plan/VERSIONS.md](../docs/plan/VERSIONS.md).

## The regression, and the lesson in its shape

The control that reveals earlier generations in the timeline stopped working: it
was pressed, and nothing widened.

A version earlier, a defect was fixed in which pressing a generation row selected
nothing. The cause then was that the pointer capture was taken on the timeline
**list**, and a browser dispatches `click` at the nearest common inclusive
ancestor of press and release — so press and release were both attributed to the
list and the row's own listener never ran. The fix took the capture on the row
that was pressed.

**That fix was keyed on rows, and the window control is not a row.** The capture
target became `row ?? the list`, the lookup returned nothing for a control that is
not a row, and the capture fell back to the list — which is precisely the
mechanism that had just been removed. The same defect reappeared on the second
control, one version later, from the fix for the first one.

The general rule, which is now what the code says: **a capture belongs to what
was pressed, and may never be taken above a control, because a capture above a
control is exactly what moves the click up.** A press inside a row takes the row;
anything else takes the element that was pressed.

## What the measurement said

The implementer's report contained two candidate causes, one of them the author's.

**The capture fallback was confirmed**, by reading the event sequence in a real
browser:

| | `pointerdown` target | `pointerup` target | `click` target |
|---|---|---|---|
| before | `button.timeline-earlier` | `section#timeline` | `section#timeline` |
| after | `button.timeline-earlier` | `button.timeline-earlier` | `button.timeline-earlier` |

And the decisive control: calling `click()` on the same button from the page moved
the list from forty rows to eighty and then to a hundred and twenty. **The wiring
was never broken; only the delivery was.**

**The second candidate was refuted.** It proposed that a later refresh reset the
window, so a press would widen it and something would immediately narrow it back.
The window is assigned in one place, once per page, and the DOM after the press
was byte-identical to the DOM at load — which is what a handler that never ran
looks like, rather than a handler whose effect was undone. A third candidate, that
re-rendering detached the listeners, was refuted the same way.

## The fix

1. The capture is taken on the element that was pressed, except that a press
   inside a row takes the row. It is never taken above a control.
2. The pan guard is shared. Making the control's click arrive means a drag that
   starts **on** the control would now widen the window as a side effect of
   panning, so the control refuses a press that travelled, exactly as a row does.
   Reverse verification showed this second change is necessary rather than
   tidy: with the capture fixed and the guard absent, the drag case fails.

## A blind spot in our own instrument, stated plainly

The browser probe reported **ten of ten checks passed** on the broken page.

Its assertions are about requests and geometry, and this control's effect is a
pure client-side rearrangement that issues no request. The probe is a tool for
asking questions, not a suite that covers an interface: it sees what the caller
declares it should see, and nobody had declared this control.

What did see it was a DOM-state script reading the row count and the control's own
label before and after a real press. That is the honest boundary, and it is the
reason the fix carries a test rather than only a probe invocation: **a tool can
help you look; only a test keeps watch.**

## A gate that was counting somebody else's writes

The full gate failed one check for a reason that had nothing to do with this
change: the dynamic isolation phase reported files written to the system
temporary directory by unrelated programs — the browser's extension-update log,
and the remote-desktop client's trace files, which that client rewrites every few
seconds. Reproduced three times by running that gate alone, with no repository
tool involved.

The gate's claim is about **this project's** tools: that they put nothing on the
system volume. Its time window cannot attribute a write to a process, so any
program that happens to write during those seconds is counted against us — which
makes the gate a coin flip on a busy machine rather than a check.

It now admits three characterised environmental classes, each naming its producer
and each specific enough not to mask a write of ours: zero-length GUID temporary
files in the system temporary directory, the browser's update log, and the
remote-desktop client's traces under a directory named for that subsystem. This
is a list of named producers, not an amnesty, and the code says so where the
list is defined.

The file had already learned this lesson once: an earlier revision tried to
re-earn its single exclusion on every run, and produced a false failure on a tree
that had not changed.

## Follow-ups

| Item | Owning version |
|---|---|
| The capture rule reads as "the row, or else what was pressed", which depends on the thing pressed being the element that carries the handler. A control added to the blank space of the list would need its own `<button>` semantics | unowned; the rule is documented |
| The pan guard is a single record, so a second finger arriving during a pan overwrites it. Pre-existing and unchanged | unowned |
| The probe cannot observe a module's internal state, only its consequences in the document; the fix for that is a declared expectation per interaction, which is a tool decision | the next version |
| The probe's evidence for this fix lives in a gitignored directory, so the before-and-after records do not survive a clean checkout | the next version |
| `scripts/viewer.ps1` still identifies a stray core by its command line, which is sometimes empty here, so its guard against a second writer fails intermittently | the next version, and it is the first item |
