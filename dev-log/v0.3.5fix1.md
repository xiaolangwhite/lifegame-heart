# v0.3.5fix1 — the migration that crashed on a real store

## Scope

Version `v0.3.5fix1` fixes a blocking defect in the version `v0.3.5` names: the
schema 2 → 3 migration raised `too many levels of trigger recursion` when it
dropped a table, so the core died on start-up, the service refused to restart it
after three attempts, and the interface was unusable. Version state is owned by
[../docs/plan/VERSIONS.md](../docs/plan/VERSIONS.md).

## What happened

Opening a schema 2 store ran `_rebuild_tables`, which issued
`DROP TABLE IF EXISTS` for each table. `lifegame_generation.parent_id` is a
**self-referential** foreign key with `ON DELETE CASCADE`. With
`PRAGMA foreign_keys=ON`, dropping a table performs an implicit `DELETE FROM` for
referential integrity, and SQLite implements a cascade as an internal trigger, so
it walks the parent chain. The person's store held **3467 rows with a parent**, in
a chain up to **1300 nodes**.

The threshold was measured rather than assumed: a chain of 1000 migrates and a
chain of 1001 fails, which is `SQLITE_MAX_TRIGGER_DEPTH` at its default of 1000.

## Why no test could have caught it, for two independent reasons

1. The schema-2 fixture was four nodes deep.
2. **The fixture's hand-written DDL omitted the foreign keys entirely** — while
   the schema that shipped declared both of them. The fixture was not a model of
   the store it stood for, so no fixture however deep could have produced this.

The second is the one worth keeping. A test whose fixture is written by hand
drifts from the thing it claims to represent, and the drift is invisible because
the fixture passes. The fixture now declares the real keys.

## The fix

The rebuild follows SQLite's documented order for changing a table's schema:

1. `PRAGMA foreign_keys=OFF`, **outside any transaction**, and the value is
   **read back** — the rebuild refuses to proceed if it did not take. This
   project has a scar here: pragmas issued inside a transaction are silently
   ignored, which once left `journal_mode` and `foreign_keys` unset while the
   cost of committing rose by a factor of about 370.
2. In one transaction: drop the three tables and create them under their final
   names, copying the rows across. There is no temporary table and no rename —
   SQLite's recipe allows one and this code does not need it, which the module
   documents follow.
3. `PRAGMA foreign_key_check` before committing; any violation rolls the whole
   thing back and is refused.
4. Commit.
5. `PRAGMA foreign_keys=ON`, read back and asserted.

Two backends gained a seam for it: `set_foreign_keys(enabled)` returning the value
actually in force — the SQLite pragma, and `@@foreign_key_checks` for MySQL — and
`foreign_key_violations()`, which for MySQL returns "not asked" rather than an
empty list, because "asked and clean" and "did not ask" are different answers and
the caller must be able to tell them apart.

A failure anywhere, including the check, rolls back and the `finally` restores
enforcement. A store that already violates its own keys is refused with the file
**byte-identical** — still schema 2, same rows, same tables.

Also corrected: `SqliteBackend.script` had a docstring claiming it ran outside a
transaction, which was never true.

## Failures

### F46 — two defects found while fixing this, one of which loses data

Both are reported rather than folded into this fix, because neither is what the
person reported and both deserve their own decision.

**`Session.truncate_after` destroys a sibling branch.** Measured: nodes
`[1,2,3,4,5]` where the working point's path is `1 → 2 → 3 → 5` and node 4 is a
live sibling under node 2; `truncate_after(0)` removes 3 and leaves `[1]`, taking
node 4's history with it. Its own docstring promises otherwise. This is a data
loss path in the tree model this project introduced two versions ago, and the
fixture for it evidently never had a sibling in the way.

**The cascade limit is not about dropping tables.** On the migrated store,
`DELETE FROM lifegame_session WHERE id = 10` raises the same error. Nothing
shipped deletes a session today — the only delete path is `truncate_after`, which
goes deepest-first — but any future feature that deletes a session meets it
immediately. The fix for the migration does not fix the mechanism.

### F47 — the fix's own limit, stated rather than implied

`foreign_keys` is a per-connection setting. "Enforcement is on" therefore means
the migrating connection ends at 1, which is asserted, and every `Store.open`
applies it, which was already tested. A fresh raw connection to the same file
reads 0 until it does so itself.
