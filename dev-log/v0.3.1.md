# v0.3.1 — the history as a tree, an interface that can get out of the way

## Scope

Version `v0.3.1` owns phase 03 milestone 01
([../docs/plan/phase-03-service-and-ui/milestones.md](../docs/plan/phase-03-service-and-ui/milestones.md)):
a recorded history that is a tree rather than a chain, so that looking at an
older state and then editing keeps the older work and shows the result as a

and delete. Version state is owned by

## State of this entry

**This version is in progress and this entry is partial on purpose.** It records

work unrecorded while it is uncommitted.

## What has landed

### The model change

A recorded generation is now a node with a parent, and the session holds a
pointer to the node the world currently corresponds to. Recording appends a child
of that pointer instead of discarding what came after it. That single change is
what the request needed: selecting an older state and then editing no longer
destroys the newer states, because the edit becomes a sibling of them.

A generation's identity therefore moved from its `(session, generation)` pair to
its own row. A fork is exactly two nodes that share a generation number, and the
old composite key could not express one.

### Schema 1 to 2, with a migration

The store's schema version moved from 1 to 2. This also closes the item the store
module had recorded as having no owner — "there is no migration path between
schema versions, and no version claims one" — and it had to be closed now, since
the version that changes the schema is the version that owes the migration.

The migration is written as read-rebuild-write rather than as a sequence of
`ALTER TABLE` statements, because the change is not additive: a column can be
added in place, but a primary key cannot be replaced in place in either dialect.
It reconstructs the parent links from the generation order, so an existing linear
history becomes a chain in the new model. The whole history is held in memory
while it runs, and that is stated in the code because it is the reason a very
large store needs room to migrate.

## Failures

### F27 — the migration inserted children before their parent

The first version of the migration inserted generations before the sessions they
belong to, and the foreign key refused it. The order is not a detail: a
generation references its session and, once branched, its own parent, so sessions
go first with a null head, then the nodes, then the head is filled in.

### F28 — the migration test's fixture was not a valid life history

With the ordering fixed, the test failed again, this time because the store's own
replay validation refused the data the test had written: two consecutive deltas
both killed the same cell. The migration was correct; the fixture was not a life
history.

Both failures were found by checks rather than by review, and the second one is
the more interesting: the validation that caught it exists to protect a rollback,
and it caught a hand-written fixture in a test about schema shape. A check that
is worth having is worth having everywhere.

## What has landed since the previous entry

**The panel.** Three states — normal, collapsed to the right, expanded to full
width — with the canvas given the space the panel gives up rather than being
covered by it. The handle stays visible in all three states, because a panel that
can hide itself and cannot be found again is a panel that loses the user's
history. A `ResizeObserver` on the canvas repaints immediately when the panel
moves or the language changes, rather than waiting for the next pushed frame.

**Tablet gestures.** Two-finger pinch zooms about the midpoint of the fingers —
the same anchoring rule as the wheel, asserted as an exact equality — and
two-finger drag pans. Pointer Events, not the deprecated touch events;
`pointercancel` edits nothing; one-finger behaviour is unchanged.

Two defects were found while building it, both of the kind that a spec does not
mention:

* **Zoom pumping.** Two fingers moving arrive as one finger moving and then the
  other. Deriving each step from the previous frame composes those intermediate
  states, so a two-finger drag zoomed in and back out — measured at
  `span 512 → 1024 → 102`. The fix is to derive every step from the gesture's
  starting sample, which removes the intermediate state rather than smoothing it.
* **The lift after a pinch counts as a tap.** When one of two fingers leaves, the
  remaining one was treated as a fresh pointer and its release as a click, which
  toggled the cell underneath. A drag that continues from a pinch is now marked
  as moved immediately.

**Archive management.** Export by name, list what the repository holds, rename in
place, delete behind a second press, and import back. Every name resolves through
one function with a regular expression and a prefix check, so a traversal — raw
or encoded — is refused with a 400 and never reaches the core.

**The core gained `open`.** The service could not import an archive without
either reimplementing the stored format in JavaScript or asking the core to do
it, and a second implementation of a format in a second language is exactly what
this project's rules exist to prevent. `open PATH` imports the archive as a new
session, loads its newest generation into the world, and makes that session the
current history. Until the command existed the route reported
`archive_import_unsupported` and the page said so in the user's language, rather
than reporting a success it had not achieved — which is the behaviour worth
keeping even now that the command exists.

## The four decisions the tree forced

These were not designed up front; each was forced by a failing test or a
contradiction the implementation exposed, and each changes what a caller can
assume. They are recorded here because they are the substance of this version.

**Recording appends.** It never discards what descends from the head. This is the
item the whole version exists for: without it, looking at an older state and then
editing deletes the newer work, which is what the previous model did.

**Reading and working on a generation are two operations.** `rollback` loads a
node and leaves the head where it was, so inspecting history is not destructive.
`checkout` — reached through the protocol's `select` — moves the head, and moving
it is what makes the next record a sibling of the existing children. The first
implementation did both in one call, and three existing tests failed. They were
right to: one operation that inspects and edits turns a look into a change.

**Amending the tip is not a branch.** An edit rewrites the head's row when
nothing descends from it, and adds a node when something does — which is exactly
the case after selecting an older node. The distinction is the difference between
editing the present and editing the past. Before it, placing a single cell
produced a second node labelled generation zero, because the edit and the
start-up record both landed on a head with no children.

**A generation number is a label, not an identity.** Two branches may hold the
same number, so `state_at` answers for the branch the world is on and **refuses**
a generation that exists only on another branch rather than guessing at it. For a
rollback the worst failure is not an error; it is a confident answer about a
state the caller did not ask for.

Two consequences worth stating plainly, because a caller will meet them:

* the store's node numbering follows the world's generation counter, so a record
  that arrives after several unrecorded steps keeps the world's number and is
  stored as a keyframe rather than as a delta that would claim a parent it never
  saw;
* a session's head is the working point, so two callers reading the same session
  see the same tree but a `select` by one of them moves it for both. One session
  is one line of work.

## What landed after the panel and the gestures

The store can record a branch and replay it: `record` appends, `checkout` and
`rollback` are separate, `path_to` walks a node's ancestors, and `state_at_node`
replays down from the nearest keyframe **validating as it goes**, so a history
that does not describe a life world is refused where it is wrong rather than
replayed into a world that looks plausible.

The protocol carries the tree: `history` names each node's id, parent and the
head, and `select` moves the working point onto a node or a generation.

The archive reader reconstructs parent links and the head. Without that an
imported session was a list of unrelated generations and nothing knew where the
world was, which the round-trip test caught.
