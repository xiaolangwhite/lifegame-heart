## Environment

Profile `M1`, unchanged: CPython 3.14.7 (uv 0.12.15) with numpy 2.5.3, Node.js
v24.19.0, GCC 16.1.0 and CMake 4.4.2 for the C++ gate, PowerShell 5.1.

Two facts about this environment decided the shape of the history layer and are
recorded rather than glossed:

* **SQLite ships with the interpreter**, so the persistence feature adds no
  dependency at all and stores its file inside the repository.
* **MySQL is not installed here** — no client, no server, no service, no
  listening port, no Python driver, and no container runtime to obtain one. That
  is why the MySQL path is implemented and its SQL generation is verified, while
  its round trip is recorded as unverified. The decision and its reasoning are
  [ADR 0011](../docs/adr/data-and-formats/0011-sqlite-default-mysql-supported.md).

### What the history layer stores

A generation is stored as a **delta** — the cells that were born and the cells
that died — because a Life generation changes a small fraction of its
population, so a delta is tens of bytes where a snapshot is eight bytes per live
cell. A **keyframe** every 64 generations bounds how far a rollback has to walk.
The load-bearing test is the rollback equivalence: a world restored to generation
*g* must equal a world stepped to *g* independently, checked for every
generation of a recorded run. Nothing weaker is evidence, because a chain that
stored the wrong deltas still produces *a* world.

The deltas come from the world rather than from a comparison of two snapshots.
Both representations hold the previous and next states side by side while
stepping, so naming the born and the dead cells costs a mask comparison; deriving
them from two snapshots would cost a scan of the population per generation, which
would have made recording — the feature — the expensive part.

Rollback replays deltas **forward** from the newest keyframe, validating as it
goes: what it kills must have been alive and what it bears must have been dead. A
corrupted chain is caught where it is corrupted rather than producing a plausible
wrong world.

## Failures

### F20 — a rollback to a generation that was not recorded returned the wrong state

`state_at(g)` found the newest keyframe at or before `g` and replayed the chain up
to `g`. If generation `g` did not exist — because the timeline had been truncated
— the replay stopped at the newest generation that *did* exist and returned
**that** state while claiming to describe `g`.

For a rollback this is the worst available failure mode: not a crash, not an
error, but a confident wrong answer that the caller cannot distinguish from a
right one. It surfaced from a test that truncated a chain to generation 3 and
then asked for generation 4, expecting a refusal. The fix is an existence check
before the replay begins.

The test was written to assert the refusal because the behaviour felt obviously
required; it was not written to *discover* anything. That is worth recording: the
defect was found by asking a question whose answer seemed too obvious to check.

### F21 — a nested `with` and a long line cannot both be satisfied

Two lint rules in this project's configuration pull in opposite directions on
`with A as a, pytest.raises(...)`: the line exceeds the limit, and splitting it
into two nested statements trips the rule that prefers one statement. The
resolution is the parenthesised form, which is both short and single. Recorded
because it will recur in every test that combines a resource with an expected
exception.

### F22 — the settings that were supposed to make the store crash-safe never ran

This is the most serious finding of the version, because it made a claim in this
project's own documentation false rather than merely incomplete.

`schema.py` declared three SQLite settings — write-ahead logging, foreign keys,
and `synchronous = NORMAL` — with a comment stating the reason plainly: the
default rollback journal does not give a guarantee that a crash cannot lose a
session, and this layer's whole purpose is that it cannot. `_create_schema` then
applied them **after** opening a transaction.

SQLite ignores `journal_mode` and `foreign_keys` inside a transaction. It does
not fail; it returns the previous value and carries on. Measured on profile `M1`
with a bare connection, comparing the two orders:

| | `journal_mode` | `foreign_keys` |
|---|---|---|
| applied outside a transaction | `wal` | `1` |
| applied inside one, as the store did | `delete` | `0` |

So the store ran on the journal its own comment said was insufficient, and the
declared `ON DELETE CASCADE` could never fire — a generation row could outlive
the session it belonged to. A controlled comparison of 200
begin-insert-commit cycles puts the cost of the same three settings at
**5.212 ms per commit** as they were, against **0.014 ms** with write-ahead
logging and `synchronous = NORMAL`: the declaration and the behaviour differed
by about three hundred and seventy times.

**Why the suite was green.** `test_a_store_creates_its_schema_on_first_open`
asserted that the file exists and that the session list is empty. Nothing
asserted that a setting took effect, so four no-ops passed every gate this
project runs.

The fix is structural rather than a moved call: the settings became
`SQLITE_CONNECTION_PRAGMAS`, a connection concern the backend applies
immediately after connecting and outside any transaction, with a `pragma()`
reader so a test can assert the *effective* value rather than the declared one.
`foreign_keys` is per-connection, so it is applied on every open, and a test
reopens the file to prove it. Two more tests were added: one that the cascade
actually deletes the history, and one that a second writer is told the store is
locked — which also gave `StoreLocked`, previously exported with no producer, a
real one.

The general lesson is the one worth keeping: **a comment claiming a guarantee is
not a test of the guarantee.** This version's record said the store was
crash-safe before anything had checked it. It is checked now.

### F23 — two more defects in the same area, found while writing the documentation

Both were found by the work item that wrote the module's contract, which is the
second time documentation review has found defects that tests did not.

* **A delta could be larger than the snapshot it replaced.** The module's reason
  for storing deltas assumes `born + died < population`, and nothing checked it.
  In a dense chaotic region every cell can change every generation: measured at
  161,952 bytes per delta against 157,136 bytes for the generation-zero snapshot,
  so the "optimisation" cost more *and* made every later rollback walk further.
  `record` now stores a snapshot when the delta would be larger, decided from
  the evidence rather than assumed.
* **`latest()` read the whole chain to discard all but its first row**, which
  makes recording quadratic in the number of generations. The measurement also
  disproved the report's own O(n²) prediction: recording 50 to 800 generations
  was flat at 5 to 9 ms, because a commit cost two orders of magnitude more than
  the query. It is a real defect and it is fixed with a `LIMIT`, and the
  measurement that says it was not yet the bottleneck is recorded with it.

## What the viewer gained, and what it cost

**A push transport.** `GET /api/events` is a Server-Sent Events stream carrying
`hello`, `frame`, `tick`, `state`, `error` and `ping`, and the page subscribes
instead of polling. Polling is kept as a tested fallback for a browser without
`EventSource` and for a stream that drops. The admission rule for a frame moved
into one module the REST route and the push hub both use, which closes the
previous version's "one constant, two copies" item.

**A representation the interface can choose.** `POST /api/representation`
exports the live set from the running core, restarts it on the other
representation, and imports the set back. Every other route answers `503` while
that happens, so a caller cannot read the empty world a restart passes through.
The generation, population and live-cell set survive the switch in both
directions, which is only true because `restore` sets the generation counter as
well as the cells — a `load` into an existing world would have left the counter
behind and made a switch look like an undo.

**Executed browser behaviour.** The page's viewport arithmetic moved into a pure
module, and a synthetic document, a recording canvas context and a controllable
event stream now drive the real page code. The drawing path asserts pixels, not
return values. This matters more than it sounds: `node --check` parses syntax and
does not resolve bindings, and the one defect that reached the rendering path —
a reference to a colour constant deleted when the palette moved into the
stylesheet — lived exactly on this zero-execution path.

Two real defects came out of building that harness, both in the new transport: a
default subscription rectangle that exceeded a small world, and an admission rule
that needed a population the core's `hello` does not carry. Two more failures
were the harness's own fault — a leaked polling timer that crossed into the next
test, and an offscreen canvas whose context had to be inspected rather than the
visible one — and are recorded as harness defects, not product ones.

## Deviations from the plan

| Planned | Delivered | Reason |
|---|---|---|
| The store's schema written for the requested database | One schema, rendered for SQLite and MySQL | The requested database is not installed here, so making it the only backend would have left the whole feature unverifiable. SQLite is the default and is verified; MySQL is supported through the same schema with an optional driver, and its round trip is recorded as an open item rather than claimed. |
| `import` resets the generation to zero | `import` accepts a generation to restore | The plan said zero because the plan was written before the switch requirement was concrete. Keeping the generation is what the acceptance criterion asks for — a switch that resets the counter looks like an undo — and the implementer followed the requirement rather than the plan. Recorded because a plan that contradicts its own acceptance criteria is a plan defect. |
| Browser coverage "automated" | Coverage of the logic and the drawing calls, not of rasterisation | No browser is available and no dependency may be added. What a synthetic document cannot check is whether a line looks crisp at a fractional device pixel ratio; that remains a human judgement and is recorded as such. |
