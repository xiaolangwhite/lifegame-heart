# v0.3.3fix1 — four defects a browser found

## Scope

Version `v0.3.3fix1` fixes four defects in the interface delivered by the version
`v0.3.3` names, all of them found by a person using it in a browser and none of
them visible to a test as it was written. Version state is owned by
[../docs/plan/VERSIONS.md](../docs/plan/VERSIONS.md).

## Why this version exists

The interface shipped with 292 green cases and eleven green gates, and its first
real session produced four complaints:

1. the preview is black after a refresh;
2. clicking a generation does not preview it, and only the step buttons move the
   selection;
3. pointing at the newest generation makes a horizontal scrollbar and that
   generation flicker against each other;
4. a white box covers part of the working-point label.

The module's own risk register had said for three versions that nothing about
what the stylesheet *does* had ever been observed. The register was right, and
this is what the first observation cost.

## The method, which is the part worth keeping

The four were not reasoned about from the source and then "fixed". They were
**measured**, in a real browser, against the real service:

- headless Edge 155, driven over the Chrome DevTools Protocol;
- the transport is Node's built-in `WebSocket`, so the module's zero-dependency
  rule is intact and nothing was installed;
- `Page.addScriptToEvaluateOnNewDocument` injects a stub API — including an
  `EventSource` that emits the handshake — **before** the page's own scripts run,
  so the page under test is the page that ships;
- `Input.dispatchMouseEvent` presses and releases for real;
- `Runtime.evaluate` reads `scrollWidth`, `clientHeight`,
  `elementFromPoint`, `getBoundingClientRect` and `getImageData`;
- `Page.captureScreenshot` for what a person actually sees.

**This capability lives in a gitignored temporary directory and is therefore not
durable.** Its source is recorded as a follow-up below, and until that is done
this version cannot be re-verified the way it was verified.

## The four, with the measurements that identified them

### F33 — the preview was never painted, and an opaque canvas composes as black

The hypothesis was that the preview was filled with the palette's dead colour.
**It was the opposite, and worse: nothing was ever drawn.** The measurement:

| Reading | Value |
|---|---|
| canvas backing store | 800x600 — the HTML attribute values, so the sizing routine had never run |
| all 480000 pixels | `0,0,0,0` |
| computed `background-color` | `rgb(255,255,255)` — the light theme's dead colour, which is what the stylesheet *wanted* to show |
| `/api/frame` requests | 0 |
| screenshot | the preview is a solid black rectangle while the rest of the page is white |

The cause is a collision between two individually reasonable decisions. The
context is created with `alpha: false`, which is right for a canvas that will be
painted edge to edge — but an unpainted opaque canvas composes as **black**, so
the background the stylesheet declares never gets a chance to appear. And every
painting path needs a preview viewport, which only a selection creates, so on a
fresh load nothing paints at all.

Fix: `paintGround()` is extracted and exported from the drawing module, and it is
used **both** as the first step of a full frame and as the whole of the
"no frame to draw" path. Two places cannot drift into two colours because there
is one place. After: the backing store resizes to the canvas, the only colour
present is the theme's dead colour, and once a selection exists the frame is
drawn (`/api/frame` twice).

### F34 — the click never reached the row, because the capture was taken on the list

The hypothesis was that the click threshold — the guard that keeps a drag from
being a click — was eating the click. **The threshold was innocent; the capture
was guilty.** The measured event sequence:

```
pointerdown -> SPAN.timeline-generation
pointerleave -> span, row, li, list      (the capture has taken effect)
pointerup   -> SECTION#timeline.timeline
click       -> SECTION#timeline.timeline
POST /api/select: never sent
```

`setPointerCapture` was called on the timeline **list**, so the capture target
took over the subsequent pointer events, and the compatibility mouse events went
with them. A `click` is dispatched to the nearest common ancestor of the press
and the release — both of which were now the list — so the row's own listener
never ran. The keyboard path was unaffected because its click is synthetic, which
is exactly why the step buttons were the only thing that worked.

Fix: the capture is taken on the row that was pressed, found from the event
target, and released from that same element. After: the press lands on the span,
the release and the click land on the button, `select` is sent, and the head and
the current marker move to the row. The threshold stays, because it is a second
and independent guard: a 48x24 pixel drag still selects nothing while a press
that does not travel still selects.

### F35 — the detail overlay widened the container it scrolls in

This one was guessed correctly in advance, and then quantified. The overlay is an
absolutely positioned element inside the scrolling container and **only its start
inset was set**, so its box was sized by its content and grew wider than the
tree. Measured while pointing at the newest generation:

| Reading | Closed | Open |
|---|---|---|
| `scrollWidth` | 319 | 329 |
| `clientHeight` | 145 | 130 |
| `elementFromPoint` at that spot | `BUTTON.timeline-row` | `SECTION#timeline` |
| `data-open` | `false` | `false`, with the overlay already 278 pixels wide |

A horizontal scrollbar appears because the overlay made the content wider, the
scrollbar takes 15 pixels of height, the row the pointer is on moves out from
under it, the pointer leaves, the overlay closes, the content narrows, the
scrollbar goes, and the loop starts again. The `false` in the last row is the
loop caught mid-flight.

Fix: **both** inline insets are set, so the box is bounded by the row, and the
content is clipped as well — so the overlay cannot contribute anything to the
container's scrollable overflow. No widening, no scrollbar, no shift, no loop.
The cycle has no input rather than a longer period.

`scrollbar-gutter: stable` was considered and rejected on the measurement: it
reserves space on the **inline** axis, and the always-present vertical scrollbar
is on that axis and never moved. The flicker came from the **block** axis, where
there is no such property. A delay, or `overflow-x: hidden`, would have hidden
the symptom while leaving the mechanism armed.

After: `scrollWidth` 319 in both states, `clientHeight` 145 in both, `data-open`
stays true, and `elementFromPoint` is still the row.

### F36 — the same overlay was 20 pixels wide while collapsed, over the label

The white box was `.timeline-overlay` itself: an element that should exist, in
the wrong geometry. Measured:

- overlay box: x=72.078, **w=20.0**, background `rgb(255,255,255)`;
- the badge in the same row: x=70.078, w=43.156, text `工作点`;
- **overlap 20 pixels, 46.3 percent of the badge** — the first two of its three
  characters, legible character by character in the screenshot.

The 20 pixels came from the collapsed state not being collapsed: the three detail
elements are zero-width, but two flex `gap`s of 8 pixels and a trailing padding
of 4 pixels are not. The offset was wrong in the other direction as well: the
start inset ignored the row's own indentation, so it sat two pixels past where
the row's second column begins.

Fix: the collapsed state sets a zero maximum inline size and carries no padding;
the start inset is derived from the row's own column geometry, including the
indentation, and the end inset is the row's own trailing padding. After: the
overlay starts exactly at the row's text column and is **0 pixels** wide when
collapsed, with an overlap of 0.

Only a row that draws its own background shows the box, which is why it appeared
on the working-point row and nowhere else — an opaque box the colour of the panel
is invisible except where it is not the colour of the panel.

## The decision this version did not make

**Loading the page does not preview the current generation.** After the fix, a
refresh shows the theme's ground with an invitation to select a generation,
rather than the newest generation's cells.

That is the module's existing design, not an oversight: its README describes the
preview as "of the generation the tree selects", the empty-state message exists
for this state, and a case asserts that no frame is asked for before there is a
selection. Changing it would be a design change to the interface rather than a
fix to it, so it is recorded here instead of being made quietly. It is also what
a person in a dark theme would see as "still black": the ground is the theme's
dead colour, which is near-black in the dark palette.

## Failures

### F37 — the new assertions were shown to fail before they were trusted

Each fix was reverted in turn and the suite re-run, because an assertion that has
never failed is an assertion nobody has tested:

| Reverted | Result |
|---|---|
| the capture moved back to the list | the two gesture cases fail, naming the capture target and the release element; a separate script asserting only behaviour also fails, with `selects: []` |
| the overlay's stylesheet rules restored | both overlay cases fail |

### F38 — the stub could not express a gesture, so the stub was extended

The synthetic document had no notion of pointer capture, so the defect in F34
could not have been written as a test. It gained a parent chain, `closest()`, an
event that bubbles, and a gesture modeller: bubbling, the capture deciding where
a move and a release go, and the click landing on the nearest common ancestor of
the press and the release.

Its limits are stated rather than assumed: it does not hit-test (a case supplies
the target and the chain explicitly), it has no geometry, and it does not raise
the boundary events that a capture change would raise in a browser. A case that
needs those dispatches them by hand.
